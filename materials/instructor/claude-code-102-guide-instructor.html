1. Parallel Development: Subagents, Worktrees & Monorepos ⏱ 15 min

Here is the situation this course is built around: your feature touches three services in one monorepo (gateway/, payments/, and notifications/). Load the whole repo into a single Claude session and two things go wrong at once. You burn tokens on code the current task never touches, and the context cross-contaminates: payments conventions leak into gateway edits, a notifications helper gets “reused” where it does not belong, and review time goes to undoing confusion rather than shipping. Over the next three hours you will build the alternative: service-scoped subagents that each see exactly one service, git worktrees that give each agent an isolated checkout, nested CLAUDE.md files that load the right rules at the right level, and Agent Teams that coordinate the whole thing against a shared contract.

From a 101 callout to a full class

In 101, the “Parallel Development Pattern” callout teased this in three sentences: /batch decomposes a large change into parallel subtasks, each in its own git worktree with a dedicated subagent. In 101 you saw the pattern in one callout; today it is the whole class: how the decomposition works, why worktrees keep agents from stepping on each other, and how to run it on a real monorepo.

2. Service-Scoped Subagents ⏱ 10 min

A subagent is a separate Claude instance that the lead session spawns to do one job with its own fresh context window. In a monorepo, the natural unit of delegation is the service: one agent that knows the payments service, one for the gateway, one for notifications. Each agent is a Markdown file in .claude/agents/: the frontmatter configures it, and the body of the file is the agent’s system prompt. The lead session reads the description field to decide when to delegate, hands the agent a task, and gets back a report instead of a wall of intermediate tool calls.

The agent file: frontmatter reference

Everything about an agent is declared in the YAML frontmatter of its .claude/agents/<name>.md file.[1] These are the fields you will use in this course:

FieldMeaning
nameUnique identifier; how the lead session (and you, in prompts) refer to the agent.
descriptionWhen to use this agent. The lead reads this to decide whether to delegate a task here.
toolsStrict allowlist of tool names the agent may call. A tool not on the list simply does not exist for this agent.
disallowedToolsExplicit denylist subtracted from the allowlist; useful to inherit defaults but carve out exceptions.
modelWhich model runs the agent (sonnet, opus, haiku, or inherit to match the lead).
effortReasoning-effort level for the agent’s model: dial down for mechanical tasks, up for design work.
maxTurnsHard cap on the agent’s turns before it is stopped (a runaway-loop budget).
colorAccent color for the agent’s entries in the transcript, so parallel agents are tellable apart.
isolationExecution isolation for the agent (e.g. running in its own worktree) so its edits stay off your checkout.
hooksPer-agent lifecycle hooks (e.g. PreToolUse) that fire only for this agent’s tool calls.
memoryPersistent memory directory for the agent, carried across sessions instead of starting blank each time.

Below the frontmatter comes plain Markdown: the agent’s system prompt. That is where you state its scope (“you own services/payments and nothing else”), its working rules, and its reporting format.

The completion-report contract

A subagent’s final message is the only thing the lead session keeps, so make it machine-checkable. The pattern used throughout this course: the agent’s system prompt ends with an instruction to close every task with a fenced JSON block in a fixed shape. 

{
  "agent": "payments-implementer",
  "task": "add an amount-format check to payments",
  "status": "green",
  "files_changed": ["services/payments/src/refunds.py"],
  "tests_run": ".venv/bin/python3 -m pytest services/payments — 12 passed",
  "notes": ""
}

The lead (or a script in CI) can parse this block instead of re-reading the agent’s whole transcript: status (green or red) gates the merge, files_changed is checked against the agent’s declared scope, and notes carries anything the orchestrator needs for the merge, including any blocked attempts worth looking at.

Write-scoping is a hook, not a permission

Subagents inherit the session’s permissions and have no per-agent cwd. The tools allowlist is all-or-nothing per tool, never per path: you can take Edit away from an agent entirely, but you cannot tell Edit “only inside services/payments” with the allowlist alone. The mechanism that stops the payments agent from editing gateway files is a per-agent PreToolUse hook that inspects the target path and exits 2 to block the call: 

hooks:
  PreToolUse:
    - matcher: "Edit|Write"
      hooks:
        - type: command
          command: "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/path_guard.py services/payments"

This block is the canonical wiring used by every scoped agent in the sample monorepo: copy it verbatim and change only the service path argument.

New agents/ directory? Restart the session

Agent files are discovered at session start. The first file you add to a brand-new .claude/agents/ directory will not load into the running session. Restart claude and it appears. Subsequent edits to existing agents are picked up normally.

3. Worktree Isolation ⏱ 10 min

Subagents that share your checkout also share your uncommitted state. Two agents editing the same tree can trample each other’s files, and a half-finished agent run leaves debris in git status that you have to untangle by hand. Worktree isolation removes the problem at the git layer: each agent gets its own checkout, its own branch, and its own blast radius.

What isolation: worktree Actually Does

Setting isolation: worktree in an agent definition changes where that agent runs. Instead of operating on your checkout, each run gets a temporary git worktree:

  • The worktree is created under .claude/worktrees/<name>, on a dedicated branch named worktree-<name>.
  • Every file the agent reads, writes, or executes lives inside that directory. Since v2.1.203, the agent’s Bash tool is confined to the worktree as well: a stray rm or test command cannot touch your main checkout.
  • The docs describe auto-cleanup: a run that ends with no changes should have its worktree and branch removed automatically. On CLI 2.1.218 we observed the worktree persisting after a no-change run (holding only the .venv symlink), so budget for manual cleanup with git worktree remove. Demo 2 shows it live.
  • If the agent did commit work, the worktree stays behind so you can inspect, cherry-pick, or merge the worktree-<name> branch on your own terms.
Housekeeping: gitignore the worktree root

Add .claude/worktrees/ to your .gitignore. Worktrees are nested inside the repo directory, and without the ignore entry every agent run pollutes git status in your main checkout: the exact noise isolation is supposed to remove. The sample monorepo ships this entry already.

The #1 Gotcha: Worktrees Branch from the DEFAULT Branch

By default, a new agent worktree branches from the repository’s default branch (usually main), not from your current HEAD.[2] If your feature spec, contracts, or scaffolding live on a feature branch, every worktree-isolated agent silently implements against code that does not contain them. The agents look busy, the diffs look plausible, and the result is wrong.

The fix is one setting in .claude/settings.json, which the sample monorepo ships: 

{
  "worktree": {
    "baseRef": "head"
  }
}

With "baseRef": "head", worktrees branch from whatever commit you have checked out: agents see the same code you see. Leave the default ("fresh") only when you deliberately want agents to start from a clean default-branch state.

The Fresh-Checkout Survival Kit

A worktree is a fresh checkout: it contains only tracked files. Two categories of things your project depends on are therefore missing, and without them every agent’s first test run fails before it does any useful work:

  1. Gitignored files the code needs: .env is the classic case. A .worktreeinclude file at the repo root lists gitignored paths that should be copied into each new worktree: 
    # .worktreeinclude — gitignored files every agent worktree still needs
.env
  2. Heavy dependency directories: .venv, node_modules. Copying gigabytes per agent is a non-starter; worktree.symlinkDirectories symlinks them from the main checkout instead, so every worktree shares one installed set: 
    {
  "worktree": {
    "baseRef": "head",
    "symlinkDirectories": [".venv"]
  }
}

    For the Node variant of the sample monorepo the list is ["node_modules"] instead. Symlinked directories are shared state: fine for read-mostly dependency trees, wrong for anything agents should mutate independently.

With baseRef, .worktreeinclude, and symlinkDirectories in place, the picture looks like this: three agents branch from the same base in parallel, work in complete isolation, and their branches merge back one at a time.

4. Nested CLAUDE.md: Hierarchical Context ⏱ 10 min

A monorepo has one repo but many contexts. The payments service cares about idempotency keys and migration order; the gateway cares about routing tables and rate limits. Stuffing all of it into one root CLAUDE.md means every session pays for every team’s notes. Claude Code solves this with hierarchical context: a CLAUDE.md per directory level, each loaded only when it is relevant.

The loading rules

Three rules govern which files reach the context window:[6]

Where the CLAUDE.md livesWhen it loads
Repo root, or any ancestor of your working directory In full, at session launch
A subdirectory below you (e.g. services/payments/) Lazily: the first time Claude reads a file in that subtree
A sibling directory you never touch Never

The third rule is the one that makes monorepos workable: a session focused on the gateway never sees the payments migration notes, no matter how long it runs. Context isolation between services is free: you get it just by putting the notes where the code is.

flowchart TD root["CLAUDE.md (repo root)

Size discipline

Lazy loading only pays off if each level stays small. The working budget: root CLAUDE.md under 200 lines, each service file under 150 lines, and zero duplication between levels. If a rule applies to every service, it belongs at the root; if it applies to one service, it belongs in that service’s file, never both. Duplicated rules drift, and the copy Claude reads last wins in ways you can’t predict.

For packages owned by other teams that you never want in your sessions at all, add their paths to claudeMdExcludes in your settings[3]: their CLAUDE.md files then stay out of context even if Claude reads a file there.

What /compact forgets

Compaction does not treat all context sources equally. After a /compact:[7]

Context sourceAfter /compact
Project-root CLAUDE.mdRe-injected from disk (survives)
Nested CLAUDE.md filesLost until a matching file is read again
Path-scoped rulesLost until a matching file is read again

So a long payments session that compacts mid-task silently drops the payments conventions it started with. This is the principled reason the next section prefers /clear + /catchup over /compact in monorepos: a fresh session replays the loading rules deterministically instead of hoping the summary kept the right notes.

5. Reading Your Token Budget ⏱ 10 min

The previous section made a claim you should not take on faith: nested CLAUDE.md files load lazily, so a scoped layout keeps most of its instructions out of the window until a file in that service is actually touched. Claude Code ships the instrument to check that claim: /context. This section teaches you to read it, and to re-measure after every change you make to your memory layout.

What /context Shows

Run /context inside any session and you get a breakdown of the context window, category by category:

CategoryWhat it contains
System promptClaude Code's own operating instructions (fixed per version, not yours to tune)
System toolsDefinitions of the built-in tools (Read, Edit, Bash, …)
MCP toolsTool schemas from every connected MCP server, growing with each server you add
Memory filesEvery CLAUDE.md and rule file currently loaded, listed by path
MessagesThe conversation so far: your prompts, Claude's replies, tool results
Free spaceWhat remains before the window fills and compaction kicks in

The row that matters for this module is Memory files. It is not just a number: it lists each loaded file by path. That list is the verification surface for the launch-time half of the previous section’s rules: after /clear on a scoped layout you should see the root CLAUDE.md only; on the flat layout, the one fat file. One caveat, measured in Demo 4: on CLI 2.1.218 the table shows the files loaded at session launch. A mid-session lazy load is proven by the InstructionsLoaded hook log from Demo 3, not by a new row here.

Do not confuse the two budget commands. /context shows what is occupying the current session's context window right now. /usage shows how much of your plan's rate limits (session and weekly) you have consumed: a billing view, not a window view.

The /clear + /catchup Pattern

When a long session bloats the Messages category, the reflex is /compact. In a nested-memory monorepo that reflex has a hidden cost: compaction summarizes the conversation, and lazily loaded CLAUDE.md files ride along in that summarization: the payments rules you triggered two hours ago may survive only as a vague paraphrase, or not at all. The window looks healthy; the instructions are gone.

The pattern that preserves correctness is /clear followed by /catchup. /clear drops the window to its baseline. /catchup (a custom command this course ships in .claude/commands/catchup.md) rebuilds exactly the working state you need by re-reading what changed. Because reading a service's files re-triggers that service's lazy CLAUDE.md load, the right nested rules come back as real files, not as summary residue. The command runs five steps:

  1. git diff main...HEAD --name-only to list the files changed on this branch (falling back to git status --short when already on main or the diff is empty).
  2. Read each changed file in full.
  3. Read the CLAUDE.md of any service whose files appear in that list, re-triggering the lazy load of exactly the rules the work needs.
  4. Summarize the state of the work in at most 10 bullets: what changed relative to main, and what is in flight.
  5. Declare which memory files are now loaded, which you verify with /context.
Measure the delta, not the total

Absolute /context numbers are not comparable across machines: your MCP servers, plugins, and Claude Code version all shift the totals. The honest measurement is the Memory files category compared between two runs on the same machine: flat layout vs. scoped layout, before compaction vs. after recovery.

6. Parallel Implementation Across Services ⏱ 25 min

Everything so far (subagents, worktrees, per-service CLAUDE.md files, token budgets) has been building toward this section. The sample monorepo ships a custom command, /implement-across-services, that takes one feature spec and implements it across all three services at the same time: one subagent per service, each in its own worktree, coordinated by the lead session you are typing into.

The spec’s Part 1.5 (your turn) section in specs/feature-refunds.md is the test case. The baseline refund flow (Part 1) already ships working; Part 1.5, a refund status lookup, is deliberately unimplemented and touches every service: payments stores and serves GET /refunds/{id}, gateway proxies it, notifications filters its events by refund_id. The services only meet at the JSON Schemas in contracts/. Three agents can build three services independently precisely because the contract, not conversation, defines where they touch.

Anatomy of the Command

/implement-across-services <spec-file> runs in four phases. The command file spells each one out so the lead session cannot improvise its way into a mess:

  1. Read the spec. The lead session reads the feature spec in full and extracts each service’s responsibilities and acceptance criteria. It does not start implementing anything itself.
  2. Spawn all three service agents in one message. The lead issues three Agent tool calls (payments, notifications, gateway) in a single response block. Each agent gets its own worktree, its own service directory, and only the slice of the spec it owns.
  3. Collect completion reports. Each agent finishes by returning a small JSON report: which branch it worked on, which files it touched, and whether its service’s tests pass. The lead does not proceed until all three reports are in.
  4. Merge sequentially, in dependency order. The lead, and only the lead, merges the three worktree branches back one at a time: payments, then notifications, then gateway, running contracts/validate.sh after each merge so a contract break is caught at the merge that introduced it.

Two passages in the command file carry most of the weight, quoted here as shipped. The first forces the fan-out to actually be parallel: 

**CRITICAL**: Run these in PARALLEL using multiple Agent tool calls in a
single message, not sequentially.

Without that line, the model will happily launch agent one, wait for it to finish, launch agent two, and so on: technically using subagents, practically sequential. Parallel tool calls in a single message are what make three agents run at once. The second passage governs the way back: 

**4. MERGE PHASE (you are the sole merger)**
- Merge each agent's worktree branch back **sequentially**, in dependency
  order:
  1. `payments`
  2. `notifications`
  3. `gateway`
- After EACH merge, run `contracts/validate.sh <service-dir>` for the service
  just merged (e.g. `bash contracts/validate.sh services/payments`).
One Merger, Always

The fan-out is parallel; the merge never is. Agents never merge their own branches: they report and stop. If three agents raced to merge into main, you would trade file conflicts (which worktrees solved) for merge conflicts (which nothing solves for free). One merger, a fixed dependency order, and a contract check between merges turns integration from a race into a pipeline.

Wall-Clock vs. Tokens

Be clear about what parallelism buys you. Three agents working at once finish in roughly the time of the slowest one, so a feature that would take three sequential agent runs lands in about a third of the wall-clock time. What it does not buy you is tokens: three agents means three separate contexts, each loading its own instructions, its own service files, and its own conversation, each billed separately. If anything, parallel runs cost slightly more tokens than one careful sequential session, because shared context (the spec, the contracts) is loaded three times instead of once.

You are spending tokens to buy wall-clock time. On a three-service feature with an afternoon deadline, that is an excellent trade. It is not always the right one.

When Sequential Is Still Right

Tiny changes. If the whole feature is a two-line edit per service, the worktree setup and triple context load cost more than they save. One session editing three files wins.

Heavy cross-service coupling. If the services need to negotiate as they go (the payload shape is still being discovered, or a contract change is part of the work), parallel agents will each guess differently and you will pay for it at merge time. Settle the contract first, or work sequentially in one context that sees all three services.

7. Contract Gates: Hooks That Push Back ⏱ 15 min

Everything so far trusts the agent to notice its own mistakes. That trust runs out the moment two agents build against the same contract: the payments agent can emit an event the notifications agent never expected, and both will happily report success. A contract gate fixes this by validating the agent’s work at the moment it tries to finish, and refusing to let it stop until the contract holds.

SubagentStop: the exit that can say no

The gate is built on one hook event: SubagentStop.[9] It fires when a subagent believes it is done, and unlike most hooks it can overrule that belief.

  • When it fires: the moment a subagent finishes its turn and tries to return control.
  • What it receives: input JSON on stdin carrying agent_type and last_assistant_message: enough to know who is stopping and what they claimed.
  • Exit code 0: the stop goes through; the subagent is done.
  • Exit code 2: the stop is blocked. Whatever the hook wrote to stderr is fed back to the agent as feedback, and the agent keeps working on it.
  • The cap: a stop can be blocked at most 8 times. After that the agent stops regardless, so a broken validator cannot trap an agent forever.

That exit-code-2 path is the whole trick. The validator does not warn, log, or hope: it bounces the agent back into its own session with the failure text in hand.

Why the gate lives in the agent’s frontmatter

You could wire a Stop hook at the session level, but there is a placement detail that matters: a hook declared in an agent’s frontmatter runs with that agent’s worktree as its working directory, and is auto-converted to SubagentStop when the agent runs as a subagent. That means validate.sh checks the agent’s actual work: the fixtures it just edited in its own worktree. A session-level hook runs from the main checkout and cannot easily find which worktree the finishing subagent was working in.

This is the canonical block, exactly as the payments agent ships it:

Stop:
  - hooks:
      - type: command
        command: "bash \"$CLAUDE_PROJECT_DIR\"/contracts/validate.sh services/payments"

Each service agent carries the same block pointing at its own service directory. The script is the shared validator from section 2’s monorepo: it loads every fixture under services/<name>/fixtures/ and checks it against the schemas in contracts/.

You Wire Hooks, You Don’t Write Them

The hooks in this course are shipped, not hand-written in class. The sample monorepo provides path_guard.py, agent_activity.py, and validate.sh ready to use: the class is about wiring them into agents and observing what they do, not about hook authoring.

8. Sparse Worktrees for Big Monorepos ⏱ 10 min

Every worktree an agent spawns is, by default, a full checkout: every service, every package, every asset in the repo gets written to disk again. On the sample monorepo that is cheap. On a real 50-package monorepo it is not: each agent pays the full checkout cost in disk and in startup time, and five parallel agents pay it five times.

worktree.sparsePaths in .claude/settings.json fixes this. When the list is present, Claude Code creates its worktrees with git sparse-checkout in cone mode: only the listed directories, plus root-level files, are written to disk. Worktrees start faster and use a fraction of the disk. In a 50-package monorepo this is the difference between seconds and minutes per agent. 

{
  "worktree": {
    "sparsePaths": [".claude", "services/payments", "contracts"]
  }
}

The Three Rules

Three rules govern how the list behaves,[3] and each one bites if you forget it:

  1. Paths are repo-root-relative. services/payments means the services/payments under the repo root, not “any directory named payments” and not a glob.
  2. All of a session’s worktrees share ONE list. There is no per-agent list. If one agent needs services/payments and another needs services/notifications, list both: every worktree in the session gets the union.
  3. Root-level FILES always come along; root-level DIRECTORIES do not. Cone mode keeps files like init.sh and .gitignore in every worktree for free, but a root-level directory only exists if it is on the list. That includes .claude itself: leave it off and worktree sessions lose their settings, deny rules, and hooks.
Pair with symlinkDirectories

Sparse paths decide what git checks out; symlinkDirectories decides which untracked directories (like .venv or node_modules) are shared into each worktree instead of being rebuilt. The sample monorepo already symlinks .venv. Together the two settings keep a worktree both small and immediately runnable.

Files Outside sparsePaths Do Not Exist

A sparse worktree does not hide excluded files: they simply are not on disk. An agent asked to read services/gateway/README.md in a worktree that only lists services/payments fails, exactly as if the file had never been committed. Keep this feature observational in class: there are known path-resolution quirks in sparse worktrees, so we watch what happens rather than build labs on top of the edge cases. The sample monorepo intentionally ships without sparsePaths: Lab 7 is where you add it.

9. Agent Teams: Coordinated Parallel Work ⏱ 30 min

Everything in this module so far follows one shape: a main session that farms work out and collects results. Subagents research and implement, worktrees keep them from stepping on each other, hooks keep the contract honest, but the workers never speak to one another. Agent teams change that shape. A team is a group of full Claude Code sessions that share a task list, message each other directly, and coordinate under a lead. Teams launched alongside Opus 4.6 (February 2026), but they are not tied to any model: the official guidance in fact recommends Sonnet for teammates, and everything in this section works that way.

Teams are experimental and off by default. Enable them with an environment variable in your project’s .claude/settings.json: 

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

The four moving parts

A team has exactly four pieces:[4]

  • Team lead: your session. It breaks the goal into tasks, spawns teammates, arbitrates disagreements, and synthesizes the result.
  • Teammates: full, independent Claude Code sessions, not lightweight subagents. Each has its own context window and works through tasks on its own.
  • Shared task list: the coordination backbone. Teammates claim tasks with file locking, so two teammates can never grab the same one. Tasks can declare dependencies; when a blocking task completes, its dependents unblock automatically.
  • Mailbox: peer-to-peer messages. Teammates can question each other’s decisions, share findings, and negotiate interfaces without routing everything through the lead.

Teammates can be spawned from the subagent definitions you already wrote in the Subagent Architecture section: mention the agent by name when you ask the lead to build the team. The definition’s tools and model fields are honored; its skills and mcpServers fields are not: teammates do not inherit those, so anything a teammate needs from a skill has to go into the task description instead.

Two control mechanisms keep a team from running away from you. First, the plan-approval flow: you can require that a teammate present its plan and get the lead’s approval before touching code. Use it for any task you would not hand to a new hire without a design review. Second, quality-gate hooks: three team events are hookable, and an exit code of 2 pushes the work back instead of letting it through.

Hook eventFires whenExit 2 means
TeammateIdleA teammate runs out of claimed workSend it back for more (e.g. its tests do not pass yet)
TaskCreatedA new task lands on the shared listReject the task (e.g. it is missing acceptance criteria)
TaskCompletedA teammate marks a task doneReopen the task (e.g. the contract validator fails)

A TaskCompleted gate that reruns the service tests looks just like the contract hooks from earlier in this module: same JSON shape, new event name, and exit 2 instead of a block message. You will wire one up in the Hard tier of Lab 8.

Subagents or a team?

This is the decision the whole module has been building toward. The two models are not rivals: they answer different questions.

SubagentsAgent team
Who coordinates The main session orchestrates everything itself The lead sets direction; teammates self-claim from the shared task list
Do workers talk to each other No: each reports back to the caller only Yes: peer-to-peer messages through the mailbox
Token cost Lower: only condensed results return to your context High: every teammate is a full session running in parallel
Best for Parallel research and well-scoped tasks where only the result matters Work that needs discussion between workers: cross-service changes, reviews that challenge each other
Teams do not isolate teammates in worktrees

Every teammate shares the working directory. Two teammates editing the same file will corrupt each other’s work exactly like two developers editing one checkout. The fix is partitioning, not isolation: give each teammate ownership of a different service’s files and say so in the task descriptions. Worktrees are the subagent story; teams are the coordination story. Do not expect one to do the other’s job.

Cost: a team is roughly 7× a single session

Every teammate burns tokens like a full session, so a team multiplies your spend by roughly the team size plus coordination overhead, about 7× for a typical setup.[8] Keep teams at 3–5 teammates, run teammates on Sonnet, and shut the team down as soon as the work lands.

Live-training note: a classroom of concurrent teams needs a generous tokens-per-minute limit. Coordinate with your org admin before the session. That is why the instructor runs Demo 8 while you run the scaled-down lab.

Known limitations

All documented, all real:[4]

  • No session resume while in-process teammates are running: finish or shut down the team first.
  • Task status can lag reality: nudge the lead to refresh if the list looks stale.
  • The lead may stop early with tasks still open: tell it to keep going.
  • One team per session: you cannot run two teams side by side.
  • No nested teams: a teammate cannot spawn a team of its own.

11. The Decision Framework ⏱ 10 min

Everything in this course reduces to one escalation ladder. Start at the cheapest rung and climb only when the task forces you to:

  1. Scoped context (nested CLAUDE.md, sparse checkout, /context): the cheapest tool. One session, small window, no coordination overhead. Most monorepo pain is solved right here.
  2. Subagents + worktrees: parallel implementation. Each worker gets its own context window and its own checkout, so N tasks run at once without stepping on each other. You pay N context windows, but zero worker-to-worker coordination.
  3. Agent teams: coordination. Workers share a task list and message each other. This is the most powerful rung and the most expensive one: every message and every shared-state read costs tokens on top of each worker's own window.

You saw the full subagents-vs-teams comparison in the agent-teams section; here it is again in compact form, because this is the distinction people mix up on Monday morning:

CommunicationReport results to the parent onlyMessage each other directly
Shared stateNone: each has its own contextShared task list + mailboxes
Token costLower: results summarized upwardHigher: coordination traffic on top
Best forIndependent, parallelizable tasksTasks that need mid-flight negotiation

The Two Questions

Notice the tree only asks two questions: do the tasks collide on files? and do the workers need to coordinate? File collisions are an isolation problem (worktrees). Coordination is a communication problem (teams). Everything else is a plain subagent.
