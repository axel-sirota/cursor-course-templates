1. Introduction

What is Cursor?

Cursor is an AI-first code editor, forked from Visual Studio Code, that deeply integrates large language models into every aspect of the developer workflow. Unlike traditional editors that bolt AI on as an afterthought, Cursor is built from the ground up to make AI your pair-programming partner.

Aspect Traditional IDE Cursor
AI Integration Plugin / Extension Native, first-class
Context Awareness Current file only Full project via Rules & Context files
Code Generation Generic completions Stack-aware, rule-enforced generation
Workflow Manual, ad-hoc Structured phases & sessions
Consistency Depends on developer Enforced via composable rules
VS Code Extensions N/A (is VS Code) Full VS Code extension compatibility

The Agentic Engineering Philosophy

This template embodies a fundamental truth: AI is context-hungry. Generic prompts produce generic code. But when you give the AI:

  • A clear technology stack (context.md)
  • Explicit rules (rules/*.mdc)
  • A structured workflow (Phase-Based Development)
  • Bounded sessions (start-session → code → next-session)

…you get consistent, professional, maintainable code that follows your standards.

The methodology works because it treats AI like a junior developer who needs clear guidance, not a magic solution that reads your mind.

“Explicit is better than implicit. Consistency is better than cleverness.”
Key Insight

The more context you provide, the better the AI performs. Rules, commands, and structured workflows are the mechanism for delivering that context consistently across every session.

Tab Completion

Cursor’s Tab autocomplete predicts your next edit as you type. It goes beyond simple token completion — it can predict multi-line blocks, suggest the next logical edit location, and even anticipate refactoring patterns.

FeatureShortcutWhat It Does
Accept suggestionTabAccept the full ghost-text prediction
Accept wordCtrl+→Accept one word at a time
RejectEscDismiss the suggestion
Next cursor positionTab (after accept)Jump to next predicted edit location
Pro Tip

Tab completion is context-aware. It reads your open files, recent edits, and active rules to predict what you’ll type next. The more rules you have, the more accurate predictions become.

Inline Edit (Cmd+K)

Select code and press Cmd+K (Mac) / Ctrl+K (Windows/Linux) to open an inline prompt. Describe what you want changed and the AI edits just that region. Perfect for targeted refactors without leaving the editor.

Chat Panel & Composer (Agent Mode)

The Chat Panel (Cmd+L) is a side panel for asking questions, debugging, and planning. It can read files you @mention but typically works on one file at a time.

Composer / Agent Mode (Cmd+I) is the powerhouse. It can:

  • Create, edit, and delete multiple files autonomously
  • Run terminal commands (build, test, lint)
  • Read your rules and context files automatically
  • Execute custom commands (@setup-stack, @architect, etc.)
  • Iterate on errors: if a test fails, it reads the error and fixes the code
When to Use Which

Tab: You know what to write, just need speed

Cmd+K: Small, targeted edit to selected code

Chat: Understanding code, asking questions, planning

Composer/Agent: Building features, TDD cycles, multi-file changes

3. Rules System

Rules are the backbone of Cursor’s AI behavior. They live in .cursor/rules/*.mdc files and tell the AI how to write code for your specific project.

Rule File Format

Each .mdc file has YAML frontmatter followed by markdown content:

---
description: Core workflow and phase-based development rules
alwaysApply: true
globs:                  # optional, for auto-attached rules
  - "app/**/*.py"
---

# Rule Title

Your rule content in markdown...

The 4 Rule Types

Type Trigger Frontmatter Use Case
Always Apply Every prompt, automatically alwaysApply: true Core workflow, coding standards
Auto-Attached When matching files are open globs: ["*.py"] Language-specific rules
Agent-Requested AI picks based on description description: "..." Situational rules (testing, deployment)
Manual User types @rule-name (no special field) On-demand references

Rule Precedence

Rules are loaded in priority order: Team > Project > User. When multiple rules apply, they are combined (not overridden) in this order.

Real Example: Core Workflow Rule

From stacks/python-fastapi/rules/000-core-workflow.mdc:

---
description: Core vibe coding workflow and phase-based development rules
alwaysApply: true
---

# Core Vibe Coding Workflow

## Workflow Phases

All feature development follows this structure:

1. **Architect Phase**: Design OpenAPI specification
2. **Phase 0 (Skeleton)**: Create all endpoints with mock responses
3. **Phase 1+ (Implementation)**: Implement each endpoint following TDD
4. **Phase Transition**: Generate summary and document learnings

## Golden Rules

### Test-Driven Development (TDD)
- E2E tests MUST be written before implementation
- Tests MUST fail initially (proves they test something)
- Implementation MUST make tests pass
- Tests MUST pass before phase transition

### Phase Transition Checklist
Before transitioning to next phase:
- [ ] All E2E tests passing
- [ ] Linting passed (ruff)
- [ ] Code formatted with Black
- [ ] Type checking passed (mypy)
- [ ] Phase summary generated

Best Practices

Rule Writing Best Practices

Numeric prefixes — Name rules like 000-core.mdc, 010-testing.mdc to control load order.

Keep rules under 500 lines — Large rules dilute the AI’s attention. Split into composable files.

Be specific — “Use snake_case for variables” beats “follow Python conventions.”

Composable over monolithic — Many focused rules beat one giant rule file.

4. Custom Commands (Slash Commands)

Commands are plain markdown files in .cursor/commands/*.md. The filename becomes the command name, invoked with the @ prefix in Cursor’s chat.

How Commands Work

When you type @setup-stack in Cursor’s chat, it loads .cursor/commands/setup-stack.md and appends it to the AI’s prompt. Any additional text you type after the command name is also sent as part of the prompt.

No templating engine — commands are pure markdown injected into context.

5. Schema-Driven Development & TDD

This methodology combines two powerful practices: Schema-Driven Development (SDD) — designing the API contract first — and Test-Driven Development (TDD) — writing tests before implementation. Together, they ensure the AI builds exactly what you designed, with proof it works.

Schema-Driven Development (SDD)

SDD means you define the shape of your API before writing any code. The schema (OpenAPI spec) becomes the single source of truth that drives everything: endpoints, request/response models, validation rules, and documentation.

SDD PrincipleWhat It MeansIn Practice
Contract First Design the API before implementing it @architect generates OpenAPI spec
Schema = Truth The spec defines what gets built Endpoints, models, and validation come from the spec
Mock First Skeleton returns fake data that matches the schema Phase 0 creates all endpoints with mock responses
Validate Shape Verify the API structure before adding logic E2E tests run against mocks to prove the shape is right
Why Schema First?

When you tell the AI “build a blog API,” you might get 10 different designs. With SDD, you lock in the contract during @architect, and the AI follows that contract exactly during implementation. No surprises, no drift.

Test-Driven Development (TDD)

TDD follows a strict Red → Green → Refactor cycle. In our workflow, the AI is required by the rules to follow this cycle. It cannot implement code without a failing test first.

# app/modules/posts/services/post_service.py

class PostService:
    def __init__(self, session: AsyncSession):
        self.repo = PostRepository(session)

    async def create(self, payload: PostCreate) -> Post:
        """Create a new blog post with validation."""
        await self._validate_author_exists(payload.author_id)
        post = Post(**payload.model_dump(), status="draft")
        return await self.repo.save(post)

    async def _validate_author_exists(self, author_id: int) -> None:
        """Raise 404 if author doesn't exist."""
        author = await self.author_repo.get(author_id)
        if not author:
            raise HTTPException(404, f"Author {author_id} not found")

6. The Workflow

The methodology is built on four core principles: Phase-Based Development, TDD, Bounded Sessions, and Context-First AI.

Phase-Based Development

PhaseGoalOutput
Phase 0 — Skeleton Build the structure. Mock every endpoint. Verify the “shape” of the API. All endpoints return mocks, E2E tests pass on stubs
Phase 1+ — Implementation Implement one endpoint at a time using TDD. Real logic, passing tests, documented phase transitions

The Command Chain

Development follows a structured chain of commands:

@setup-stack → @architect → @start-session → (code) → @code-review → @next-session

Three Workflows

Workflow 1: Fresh Project with Known Stack

  1. Clone the template: git clone <repo>
  2. Open in Cursor: cursor .
  3. Configure stack: @setup-stack — choose from python-fastapi, node-express, java-spring, go-gin, devops-terraform, or blank
  4. Design your feature: @architect "Build a task management API"
  5. Start coding: @start-session

Workflow 2: Fresh Project with Custom Stack

  1. Clone the template
  2. Create stack structure: stacks/my-stack/rules/
  3. Define stack context: stacks/my-stack/context.md
  4. Create rules (.mdc files)
  5. Optional: add templates and examples
  6. Configure: @setup-stack
  7. Build: @architect → @start-session

Workflow 3: Existing Codebase (Brownfield)

  1. Copy .cursor/ config into your existing repo
  2. Open in Cursor
  3. Auto-detect: @detect-stack
  4. Review context, set Strictness: Low for legacy code
  5. Start working: @start-session

8. Hooks Beta

Hooks are lifecycle interceptors defined in .cursor/hooks.json. They let you run shell commands or inject prompts before or after specific AI actions.

Beta Feature

Hooks are currently in beta. The API surface may change. Enable them in Cursor Settings → Beta → Hooks.

hooks.json Format

{
  "hooks": {
    "postToolUse": [
      {
        "matcher": {
          "tool_name": "edit_file"
        },
        "commands": [
          {
            "type": "command",
            "command": "npx prettier --write $FILE_PATH"
          }
        ]
      }
    ],
    "beforeShellExecution": [
      {
        "matcher": {
          "command_pattern": "rm -rf /"
        },
        "commands": [
          {
            "type": "command",
            "command": "echo 'BLOCKED: Dangerous command' && exit 2"
          }
        ]
      }
    ]
  }
}

Hook Types

TypeRunsUse Case
Command ("type": "command") Shell command Format code, run linters, block dangerous ops
Prompt ("type": "prompt") Injects text into LLM context Add reminders, enforce conventions

Exit Codes

Exit CodeMeaningBehavior
0SuccessAction proceeds normally
2BlockAction is prevented
OtherFailureFail-open: action proceeds anyway
Fail-Closed Exceptions

Two events are fail-closed by default: beforeReadFile and beforeMCPExecution. If the hook fails (non-zero, non-2), the action is blocked instead of proceeding.

Configuration Levels

Hooks are merged in priority order:

Enterprise → Team → Project → User

Higher-priority hooks run first. Enterprise hooks cannot be overridden.
