Section 1: Introduction and Philosophy

Estimated time: 10 minutes

Welcome to this course on structured, agentic development with Cursor IDE. Before diving into commands, rules, or code generation, we need to establish the foundational mindset that separates developers who get mediocre results from AI tools from those who get consistently excellent results. That mindset is Agentic Engineering.

This section answers three questions: What is the Agentic Engineering philosophy? What will you learn in this course? And how does agentic development differ from the ad-hoc approach most developers start with?

1.1 The Agentic Engineering Philosophy

Every AI coding tool — Cursor, GitHub Copilot, Claude Code, or any other — is, at its core, a context-processing machine. It reads context, it generates text that continues that context. That single insight explains why so many developers feel disappointed by AI tools after their initial excitement: they treat the AI like a search engine, typing short, vague queries and expecting brilliant answers. Then they wonder why the output is generic, inconsistent, or just wrong.

Core Insight: AI is context-hungry. The quality of AI output is almost entirely determined by the quality of context you provide. Generic prompts produce generic code. Structured context produces structured, reliable code.

Think about what happens when you ask a senior engineer to implement a feature with no context versus when you hand them a well-written specification, the relevant existing code, the test requirements, and your team's coding standards. The difference in output quality is enormous — and the exact same dynamic applies to AI. The model is not the bottleneck. Your context is the bottleneck.

The Four Pillars of Structured Agentic Development

This course teaches a methodology built on four mutually reinforcing pillars:

  • Spec-Driven Development (SDD): Before writing a single line of code, you write a structured specification. The spec becomes the AI's primary context. When the AI knows what you are building, why, what the inputs and outputs are, and what the acceptance criteria look like, it produces code that actually matches your intent.
  • Rules: Your team's coding standards, architecture decisions, and style conventions are encoded as .cursorrules files. Every AI interaction in your project automatically inherits these rules. Consistency stops being a discipline problem and becomes a structural guarantee.
  • Commands: Repetitive, multi-step workflows — "review this PR", "write tests for this function", "refactor to use the repository pattern" — are encoded as slash commands. You invoke them with a single keystroke. The AI executes a consistent, repeatable process every time.
  • Test-Driven Development (TDD): Tests written before implementation give the AI a precise, executable specification of correct behavior. The AI is not guessing what "correct" means — it can run the tests and verify its own output. This dramatically reduces hallucination and drift.
"Explicit is better than implicit. Consistency is better than cleverness." — The Agentic Engineering Principle

This quote deserves unpacking. "Explicit is better than implicit" means you should never rely on the AI inferring your intent from vague instructions. Say what you mean. Write it down. Put it in a spec, a rule file, or a command definition. "Consistency is better than cleverness" means a workflow that produces good-enough results every single time is more valuable than a clever prompt that occasionally produces something brilliant but usually produces something unpredictable. Agentic Engineering optimises for repeatability, not occasional magic.

The more structure you give the AI, the better it performs. This is not a limitation — it is a feature. It means that your investment in writing clear specifications, encoding rules, and building commands compounds over time. Each spec you write makes the next one faster. Each rule you encode eliminates an entire class of inconsistency. Each command you build turns a 10-step process into one keystroke.

Traditional vs Agentic Development: A Side-by-Side View

To make this concrete, consider how the same task — implementing a new feature — plays out under traditional ad-hoc AI usage versus the structured agentic approach.

In the traditional approach, a developer opens a chat, types something like "write a function to handle user authentication", gets some code back, pastes it in, runs it, discovers it does not match the project's patterns, manually edits it, asks for fixes, and repeats. There are no rules governing what the AI produces. There is no specification the AI can reference. Every session starts from scratch. The developer is essentially doing code review and manual correction as a constant overhead on every AI interaction.

In the agentic approach, the developer starts by writing or retrieving a spec for the feature. The AI reads the spec, the relevant rules, and the existing codebase context. It generates code that is already consistent with the project's patterns because those patterns are encoded in rules. The developer runs the tests — which were specified before implementation — and the AI iterates until they pass. A command handles the review step. Session transitions are managed so context is never lost between working sessions. The developer's cognitive load drops dramatically because the structure does the heavy lifting.

Notice the loop in the traditional workflow. Because there is no upfront structure, the developer is trapped in a fix-and-retry cycle. The agentic workflow is a pipeline — each phase hands off to the next with clear artifacts. There is still iteration, but it is structured iteration bounded by tests, not unbounded manual debugging.

Key Takeaway: The agentic approach does not make you dependent on AI — it makes you effective with AI. You are in control of the structure. The AI executes within that structure. You get the leverage without losing authorship.

1.3 Setting Expectations: What Agentic Engineering Is Not

Before moving on, it is worth being direct about what this methodology is not, because there is a lot of hype in this space and hype creates unrealistic expectations that lead to frustration.

Agentic Engineering is not about removing developers from the loop. You will still write specifications. You will still review generated code. You will still make architecture decisions. The AI handles execution within a structure you define. You remain the author; the AI is a very fast, very capable pair programmer who needs clear direction.

Agentic Engineering is not a shortcut around understanding your codebase. In fact, writing good specs requires deep understanding of what you are building. The methodology rewards developers who think carefully about design before writing code — which is just good engineering practice, with or without AI.

Agentic Engineering is not tool-specific. While this course uses Cursor, the principles apply to any AI-assisted development environment. The concepts of spec-driven context, encoded rules, and command-driven workflows translate directly to Claude Code, GitHub Copilot Workspace, and future tools we cannot yet anticipate. You are learning a methodology, not just a set of Cursor features.

What Agentic Engineering is is a structured, repeatable way to collaborate with AI that produces consistent, high-quality results at a pace that would be impossible without AI assistance. That is a meaningful claim, and the rest of this course is the evidence for it.

2. The Workflow — Spec-Driven Development

The single most important lesson in this course is not a keyboard shortcut or a clever prompt — it is a methodology. Without a structured workflow, AI-assisted development devolves into what the industry calls "vibe coding": asking the AI to build things in an ad-hoc stream of consciousness, accumulating technical debt with every session, and eventually losing track of what the codebase is supposed to do.

This section introduces Spec-Driven Development (SDD) — the architectural philosophy that underpins everything else in this course — along with the Phase-Based Development and Session-Based workflow patterns that make it practical.

2.1 What is Spec-Driven Development?

Spec-Driven Development is an industry-recognized methodology, featured in the ThoughtWorks Technology Radar 2025, that inverts the traditional software development workflow. In conventional development, you write code first and document it (if at all) as an afterthought. SDD flips that: the specification comes first, and the code is derived from it.

The core insight is simple but powerful: an AI model that receives a precise, structured specification produces far more consistent, correct, and maintainable code than one that is given a vague natural-language description. By anchoring every coding session to a formal spec, you give the AI an unambiguous source of truth to build against.

“Code drifts. Specs don’t. Anchor the AI to the spec, and the code stays honest.”

SDD manifests in three progressively sophisticated patterns. Understanding where they sit on the spectrum helps you choose the right level of rigor for your team.

Pattern Core Idea Best For Our Use
Spec-First Design the API contract (OpenAPI, entities, endpoints) before writing any implementation code Individual developers, small teams, learning environments Yes — this course
Spec-Anchored Spec governs the entire SDLC; changes require spec approval; full audit trail Enterprise teams, regulated industries, multi-team APIs Optional extension
Spec-as-Source The spec is the source — code, tests, mocks, and docs are all generated from the spec Mature platform engineering teams with strong tooling Not in scope

We use the Spec-First Pattern — the lightest, most accessible form of SDD. You design the API contract once, in one session, before a single line of business logic is written. That contract then governs every subsequent AI interaction. It is the ceiling and the floor: the AI cannot add endpoints you did not spec, and it cannot skip endpoints you did.

What Is an "API Contract"?

In this context, an API contract is a formal description of your service’s interface: the endpoints, their HTTP methods, the request and response schemas, the HTTP status codes, and the domain entities. We express this as an OpenAPI 3.x specification (a YAML or JSON file). The contract does not describe implementation details — only the observable shape of the API.

2.2 SDD vs TDD: Complementary, Not Competing

A common source of confusion is how Spec-Driven Development relates to Test-Driven Development (TDD). They sound similar, and both emphasize “define before implement” — but they operate at entirely different layers of the development process. Understanding this distinction prevents you from thinking you have to choose one over the other.

Think of it this way: SDD answers the architectural question (“what are we building, and what does it look like from the outside?”) while TDD answers the implementation question (“how do we prove that each piece of logic works correctly?”). SDD operates at the level of API contracts, domain models, and endpoint shapes. TDD operates at the level of individual functions, edge cases, and business rules. They reinforce each other: the spec gives tests a fixed, authoritative target to assert against.

Approach Layer Answers Artifact When
SDD (Spec-First) Architecture / Contract What to build OpenAPI spec, entity models Phase 0, before any code
TDD Implementation How to prove it works Unit tests, integration tests Phase 1+, endpoint by endpoint
BDD Behaviour / Acceptance Whether stakeholder goals are met Gherkin scenarios, feature files Alongside stakeholder sign-off
Vibe Coding None Whatever the AI guesses Mystery code, no spec, no tests Never (in production)
The Key Insight

SDD and TDD are not alternatives — they are stacked layers. SDD comes first and defines the contract. TDD comes second and verifies each piece of logic satisfies that contract. Every green test is a proof that your implementation matches what the spec promised.

2.3 Our Spec-First Workflow

The Spec-First Workflow has three distinct stages. Each stage is a gate: you do not move forward until the current stage is complete. This discipline is what separates professional AI-assisted development from vibe coding.

Stage 1 — Design the contract with /architect. You describe the feature in plain English to the /architect command. The AI produces an OpenAPI specification, a list of domain entities, and a breakdown of endpoints. This is a conversation, not a one-shot generation: you review the output, challenge assumptions, and iterate until the spec reflects what you actually want to build. At the end of this stage you have a specification document you would be comfortable sharing with a colleague or a client — before touching any implementation code.

Stage 2 — Build the skeleton (Phase 0). With the spec as the blueprint, the AI scaffolds the entire project: directory structure, router files, model files, and mock endpoint handlers. Every endpoint in the spec gets a corresponding route that returns a hardcoded mock response with the correct schema. At this stage, nothing is real — but everything is shaped correctly. You can run the application, open the Swagger UI, and see every endpoint listed with its documented request and response types.

Stage 3 — Implement with TDD (Phase 1+). Now you implement one endpoint at a time. For each endpoint, you first update the test to assert real business logic (not just mock data), watch it fail (red), implement the logic to make it pass (green), then refactor (blue). The spec is always the reference: if an implementation deviates from the spec, the spec wins.

The Most Common Mistake

Jumping straight from /architect to implementation without building Phase 0 first. The skeleton stage looks like busy work, but it is not — it validates the API shape before you invest time in business logic. Finding a design flaw at Phase 0 costs five minutes. Finding it after four endpoints are implemented costs hours.

2.4 Phase-Based Development

The Spec-First Workflow is structured into numbered phases. Phases are explicit checkpoints that prevent the most common failure mode in AI-assisted development: getting so deep into implementation details that you lose sight of the overall architecture. Phases enforce the discipline of proving each layer works before building the next layer on top of it.

Phase 0 (Skeleton) is entirely structural. Its job is to prove that the application can be built, not to prove that the logic is correct. You scaffold the directory layout, create every file the spec requires, wire up every route, and return mock responses from every handler. When Phase 0 is complete, a fresh developer joining the project can run the app, browse the API documentation, and understand the entire surface area of the system — with zero business logic implemented.

Phase 1 and beyond are implementation phases. Each phase typically covers a logical group of endpoints (e.g., all authentication endpoints, all user management endpoints, or all task CRUD endpoints). Each endpoint follows a strict red-green-refactor TDD loop. Phase 1 does not end until every endpoint in scope has real tests and real implementations.

The phase transition is a formal checkpoint. Before moving from Phase 0 to Phase 1, or from Phase 1 to Phase 2, you run /code-review to audit the current state against your rules, then /next-session to document what was accomplished and set up the context for the next phase. This creates a clear paper trail: anyone who reads the session history can understand exactly what was built, in what order, and why.

Phase Goal Tests Passing? Real Logic? Exit Criteria
Phase 0 Prove API shape Yes (on mocks) No All endpoints return correct shape; pytest green
Phase 1 Implement core endpoints Yes (on real logic) Yes All Phase 1 endpoints pass real assertions; no mocks remain
Phase N Implement remaining scope Yes Yes All spec endpoints implemented; full test suite green
Why Not Just Write All the Code at Once?

AI models have a limited context window and will drift over a long conversation. By the time you are implementing your fifth endpoint in a single session, the model may have forgotten the naming conventions from your first endpoint, or the error handling pattern you established in the second. Phases + sessions keep the context small and focused, which keeps the output consistent and correct.

2.5 Session-Based Workflow

AI language models do not retain memory between conversations. Even within a single long conversation, context quality degrades as the conversation grows: early instructions get pushed further away from the model’s attention window, and subtle drift accumulates. The session-based workflow is the practical solution to this fundamental constraint.

A session is a bounded unit of work. It has a defined start, a single focused goal, and a formal end. You do not try to build an entire feature in one session. You pick one endpoint, or one layer, or one concern, complete it, review it, document the transition, and start a fresh session for the next unit. Fresh context produces consistent code.

Starting a session with /start-session does more than open a new chat window. The command reads your .cursor/context.md, the active session plan, any open issues or notes from the previous session, and injects all of that into the AI’s context before you write a single prompt. The AI begins the session already knowing the stack, the rules, the phase, and the specific goal — without you having to re-explain any of it.

During execution, you stay focused on one thing. The session is not over when the feature works — it is over when the tests pass, the code is clean, and the output matches the spec. Resist the temptation to fix a nearby bug or add an unrelated endpoint “while you’re at it.” Context pollution is how sessions spiral into unreviewed, inconsistent code.

Ending a session with /next-session generates a structured transition document: what was completed, what tests pass, what the next session should pick up, and any decisions or open questions to carry forward. This document becomes the starting context for the next call to /start-session. The loop is self-sustaining.

Sessions Are Not Optional

The most experienced developers on this workflow run the full /start-session → execute → /next-session loop every single time, even for tiny changes. The overhead is less than two minutes. The benefit is a codebase where every session is auditable, the AI never drifts from the rules, and you can hand off to a teammate — or resume after a week’s break — without losing context.

Putting it all together: SDD gives you the contract, Phase-Based Development gives you the structure to build against that contract incrementally, and the Session-Based Workflow ensures the AI stays aligned with your rules and context throughout the entire process. These three patterns are not independent techniques — they are designed to work as a single, coherent system.

3. Skills — Slash Commands (20 min + Lab 2)

Commands are the productivity backbone of the Cursor AI workflow. They let you encode complex, multi-step workflows into a single keystroke, ensuring every session starts with the right context and follows the right process — automatically.

Critical Syntax Rule: / vs @

Commands are invoked with a forward slash: /setup-stack, /architect, /start-session.

The @ symbol is exclusively for attaching context: @app/api/posts.py, @codebase, @web.

Never write @setup-stack or @architect to invoke a command — those forms are incorrect. The correct invocation is always /command-name.

What Are Commands?

A command is nothing more than a plain markdown file stored in .cursor/commands/. The filename determines the command name: setup-stack.md becomes /setup-stack, start-session.md becomes /start-session, and so on.

When you type /start-session in Cursor’s Agent panel, Cursor reads that markdown file and injects its entire contents into the AI’s prompt as a system-level instruction. There is no templating engine, no compilation step — pure markdown, injected as context.

This is how you encode complex, repeatable workflows as reusable prompts. Instead of retyping “read the context file, check the rules, load the phase…” on every session, you type /start-session and the full workflow fires.

How Commands Work Under the Hood

Cursor searches for .cursor/commands/<name>.md (project-level) or ~/.cursor/commands/<name>.md (user-level), reads the file, and prepends its body to the AI prompt — before your message. The AI sees the full command instruction set, then your request, in a single prompt turn.

/ vs @ — The Critical Distinction

Two Symbols, Two Completely Different Jobs

/command-name — invokes a command. Cursor loads the corresponding .md file and executes the workflow it contains.

@symbol — attaches context. It tells Cursor to include a file, folder, web search result, or codebase index in the prompt.

Syntax What It Does Example
/setup-stack Invokes the setup-stack command workflow Configures project stack from scratch
/architect "Build a blog" Invokes architect command with your description Designs API spec and generates skeleton
/start-session Invokes session-start workflow Loads context, phase, and strictness level
@app/api/posts.py Attaches a specific file as context AI can read that file during the session
@codebase Searches the entire codebase semantically AI finds relevant code across all files
@web Includes live web search results as context AI can reference current documentation

A verification agent is a focused subagent — a separate AI invocation with a narrow prompt and a single concern. The persona pack ships with several:

Section 4: Rules System 20 min + Lab 3

Rules are the mechanism that makes Cursor's AI write your style of code instead of generic code. Every rule file is injected silently into matching AI prompts — you write the rule once and the AI obeys it on every prompt, forever.

What Are Rules?

Rules live in .cursor/rules/ as .mdc files (Markdown with a YAML frontmatter header). Cursor reads every file in that directory and, based on the frontmatter, decides which rules to inject into the AI's context before it sees your prompt.

  • .mdc files — plain text files: YAML frontmatter on top, Markdown body below.
  • Injected automatically — you never paste your standards into the chat; Cursor does it for you.
  • Enforce your style — snake_case, TDD, phase gates, logging patterns — whatever matters to your team.
  • Rules + Commands = complete guardrails — Commands define workflows; Rules define standards. Together they make the AI a disciplined team member.

Rule File Format

Every .mdc file follows this exact structure:

---
description: Core workflow and phase-based development rules
alwaysApply: true
globs:
  - "app/**/*.py"
---

# Rule Title

Rule content in markdown...
  • description — One-line summary. The AI reads this to decide whether to load the rule when in Agent-Requested mode.
  • alwaysApply — Boolean. When true, the rule is loaded on every prompt regardless of context.
  • globs — File patterns. When any open or edited file matches, the rule is auto-attached.
  • The body is plain Markdown — headings, lists, code blocks, checklists. The AI understands all of it.

The 4 Rule Types

Cursor supports four distinct loading strategies. Choose the right one for each rule to keep context lean and focused.

Type Frontmatter signal When it loads Best used for
Always Apply alwaysApply: true Every single prompt, no exceptions Core workflow rules, phase gates, TDD enforcement, global coding standards
Auto-Attached globs: ["*.py"] When a matching file is open or being edited Language-specific style (Python, TypeScript), framework-specific patterns (FastAPI, React)
Agent-Requested Only a description field (no alwaysApply, no globs) AI reads all descriptions and pulls the rule when it judges it relevant Situational rules — Docker deployment, database migration steps, security checklists
Manual No special frontmatter User explicitly types @rule-name in the chat Reference material, rarely-needed standards, legacy migration guides

Always Apply

The most powerful type. Use it for rules that must never be skipped — phase-based development workflow, TDD golden rule, secrets management. The tradeoff is token cost: every prompt pays for these rules. Keep them focused and under 200 lines each.

Auto-Attached

Scoped by file pattern. A Python style guide with globs: ["app/**/*.py"] loads only when you are editing Python files — your TypeScript work is unaffected. This keeps context clean and tokens low.

Agent-Requested

The AI autonomously decides when to pull these in, based on the description field. Write descriptions that are concrete and action-oriented: "Docker Compose deployment rules for staging environment" is far better than "deployment stuff".

Manual

You are fully in control. Type @700-logging in the chat when you want that rule active. Good for one-off tasks or rules so specialized they should never load automatically.

Rule Loading Decision Tree

Rule Precedence and Stacking

When multiple rules match, Cursor combines them — it does not pick a winner and discard the rest. All matching rules are stacked into one combined context block injected before your prompt.

  • Load order: Numeric file prefixes control the order — 000-core.mdc loads before 100-style.mdc. Put foundational rules at lower numbers.
  • Team > Project > User: Team-level rules (committed to the repo) take precedence over personal user rules.
  • Rules stack, not override: A later rule adds to context; it does not erase earlier rules. Design rules to be composable — each focused on one concern.

How Rules Enforce Spec-Driven Development

Spec-Driven Development (SDD) depends on phases being respected — you cannot implement before designing, and you cannot merge before tests pass. Rules encode these gates directly into the AI's context so it enforces them without you having to remind it every prompt.

### Always Setup Virtual Environment First

- Tests MUST fail initially (proves they test something)
- Implementation MUST make tests pass
- Tests MUST pass before phase transition

- Use type hints for all function signatures
- Write docstrings for all public functions and classes

Composable Rules Beat Monolithic Rules

One 2,000-line rule file is worse than ten 200-line rule files. The AI's attention degrades as context grows. Focused, composable rules keep each concern sharp:

  • 000-core-workflow.mdc — phase gates and TDD only
  • 100-architect-phase.mdc — spec-first design only
  • 500-python-style.mdc — Python code standards only
  • 700-logging.mdc — structured logging only

Each rule loads only when relevant. The AI gets exactly the context it needs — nothing more, nothing less.

Keep rules under 500 lines. Large rule files dilute AI attention. If a rule is growing unwieldy, split it into two focused files with adjacent numeric prefixes (e.g., 500-python-style.mdc and 510-python-async.mdc).

Rule Best Practices

  • Use numeric prefixes — 000-, 100-, 200- — to control load order and make the priority hierarchy obvious at a glance.
  • Be specific — "Use snake_case for all variable and function names" beats "follow Python conventions". The AI needs unambiguous instructions.
  • Composable over monolithic — one rule, one concern. Makes rules easier to maintain, override, and reason about.
  • Always Apply for workflow rules — phase gates and TDD enforcement must never be skipped, so they belong in alwaysApply: true rules.
  • Globs for language/framework rules — Python style rules have no business loading when you are editing a Dockerfile. Use globs to scope them.
  • Descriptive descriptions — the Agent-Requested mechanism is only as good as your description fields. Write them as if explaining to a new engineer what the rule does and when it applies.
  • Version-control your rules — rules are code. Commit them, review them in PRs, and iterate on them as your team's standards evolve.

Section 5: Adapting the Workflow to Existing Codebases 20 min + Lab 4

Everything you have learned so far — Spec-Driven Development, slash commands, rules — was demonstrated on a greenfield project: a fresh codebase with no history, no legacy patterns, no constraints. But most real-world development is brownfield: you inherit an existing codebase with its own conventions, tech debt, and unwritten rules. This section teaches you how to bring the Agentic Engineering methodology into an existing project without breaking what already works.

5.1 When Greenfield Isn’t an Option

Greenfield projects are the exception, not the norm. Most engineers spend their careers working in codebases that are months or years old, written by other people, with patterns they didn’t choose. The Agentic Engineering methodology still applies — but it needs adaptation.

The core challenge with brownfield AI assistance:

  • The AI doesn’t know your codebase’s conventions unless you tell it
  • Applying “full standards” to legacy code creates noise, not value
  • Existing patterns may conflict with best practices — and that’s OK
  • The goal is to improve new code without destabilising old code
The Cardinal Rule of Brownfield: Never let the AI refactor existing code unless you explicitly asked for it. The cost of breaking working legacy code always exceeds the benefit of making it “cleaner”.

5.5 Common Pitfalls

  • AI ignores your rules. Check that every .mdc file has alwaysApply: true in the frontmatter. Rules without this flag are silently skipped.

  • Rules conflict with existing patterns. When your codebase uses camelCase but the stack rule says snake_case, the AI gets confused. Always align rules with what /detect-stack found, not with the ideal convention.

Section 6: MCP Servers 15 min + Lab 5

What is the Model Context Protocol (MCP)?

The Model Context Protocol (MCP) is an open standard created by Anthropic for connecting AI agents to external tools and data sources. MCP servers are lightweight programs that expose tools to the AI through a standardized protocol, dramatically expanding what the AI can do during a session.

Without MCP, the AI only knows what you paste into the prompt. With MCP, it gains access to live external data: real databases, APIs, file systems, GitHub repositories, and documentation sites. Think of MCP servers as plugins that extend what the AI can do — instead of reasoning from static training data, it can actively query your real systems.

Why MCP Matters for Development

The difference MCP makes in practice:

  • Without MCP: AI only knows what you paste into the prompt
  • With MCP: AI can query your database, check your GitHub issues, look up live docs, call your API

Practical examples of what MCP unlocks:

  • Query your Postgres database to understand existing data structures and content
  • Fetch GitHub issues to understand what needs to be built next
  • Check live API documentation instead of relying on potentially outdated training data
  • Read and write to your file system in a sandboxed, structured way

How MCP Works in Cursor

MCP servers are configured in .cursor/mcp.json (project-level) or ~/.cursor/mcp.json (global, applies to all projects). Cursor starts the configured MCP servers at launch and makes their tools available throughout Agent mode. The AI agent can call MCP tools just like any other built-in capability — editing files, running terminal commands, etc.

Two transport types are supported:

  • stdio — runs a local process on your machine (most common)
  • http — connects to a remote MCP server over HTTP

Configuration Format

The .cursor/mcp.json file uses the following structure:

{
  "mcpServers": {
    "server-name": {
      "command": "npx",
      "args": ["-y", "package-name"],
      "env": {
        "API_KEY": "your_key"
      }
    }
  }
}
Important: Restart Cursor after adding MCP servers. MCP servers are loaded only at startup. After editing .cursor/mcp.json, you must fully quit and relaunch Cursor for the new servers to become available in Agent mode.

Popular MCP Servers

These MCP servers cover the most common development use cases:

  • @modelcontextprotocol/server-filesystem — Read and write files in a sandboxed, controlled way
  • @modelcontextprotocol/server-fetch — Make HTTP requests (great for testing your own running API)
  • @modelcontextprotocol/server-github — Read issues, pull requests, and repository data from GitHub
  • @modelcontextprotocol/server-postgres — Query a PostgreSQL database directly from the agent

The Cursor Marketplace at cursor.com/marketplace (live since February 2026) provides one-click install for a growing library of community and official MCP servers.

MCP vs Context Symbols (@)

It is worth understanding the distinction between MCP tools and the @ context symbols you have already used:

  • @web and other @ symbols are passive and read-only — they inject static context into your prompt at the moment you send it.
  • MCP tools are active — they can read and write, query live databases, call APIs with authentication, and perform stateful operations during the agent's execution.

Use @ symbols for injecting static context (files, docs, web pages). Use MCP when you need dynamic, interactive access to live systems.

Important Notes

  • Project vs global config: .cursor/mcp.json in your project overrides ~/.cursor/mcp.json for any server with the same name. This lets you have per-project database connections while keeping global utility servers available everywhere.
  • Keep secrets safe: Store API keys in environment variables referenced via the env block — never hardcode sensitive values directly in mcp.json, which may be committed to source control.

Section 7: Hooks — Lifecycle Automation Beta 15 min + Lab 6

7.1 What Are Hooks?

Hooks are lifecycle interceptors — shell commands or prompt injections that run automatically before or after specific AI actions. They operate in the background, invisibly, forming the automation layer that sits between the AI agent and the tools it uses.

Hooks are defined in .cursor/hooks.json at the project, user, team, or enterprise level.

Why Use Hooks?

  • Auto-format files on every AI edit (Prettier, Black, gofmt)
  • Block dangerous commands before they execute (rm -rf, DROP TABLE)
  • Run linters or type-checkers after every file change
  • Trigger tests automatically after an edit
  • Send Slack/webhook notifications on agent actions
  • Inject additional context into the LLM before it responds

7.2 hooks.json Format

The file lives at .cursor/hooks.json in your project root (or at the user/team/enterprise config path). The top-level key is "hooks", containing an object keyed by lifecycle event name. Each event maps to an array of hook objects with a matcher and a commands list. 

{
  "hooks": {
    "postToolUse": [
      {
        "matcher": {
          "tool_name": "edit_file"
        },
        "commands": [
          {
            "type": "command",
            "command": "npx prettier --write $FILE_PATH"
          }
        ]
      }
    ]
  }
}

Key fields:

  • matcher — criteria for when this hook fires (tool name, file glob, command pattern)
  • commands — ordered list of actions to execute when the matcher hits
  • type — either "command" (shell) or "prompt" (LLM context injection)
  • command — the shell string to run; environment variables like $FILE_PATH are available

7.3 Lifecycle Events

Cursor exposes the following lifecycle events across six categories:

Category Event When It Fires
Session sessionStart When a new AI session begins
sessionEnd When the AI session ends or is closed
Tool preToolUse Before the AI calls any tool (edit, read, shell, etc.)
postToolUse After a tool call completes successfully
postToolUseFailure After a tool call fails or returns an error
Shell beforeShellExecution Before any shell command is executed by the AI
afterShellExecution After a shell command finishes executing
File beforeReadFile Before the AI reads a file (fail-closed by default)
afterFileEdit After the AI writes or edits a file
MCP beforeMCPExecution Before an MCP tool is called (fail-closed by default)
afterMCPExecution After an MCP tool call completes
Agent afterAgentResponse After the AI agent produces a response
stop When the agent stops or is interrupted
Prompt beforeSubmitPrompt Before the user's prompt is sent to the LLM

7.4 Hook Types

Each entry in commands has a type field that determines what happens when the hook fires:

"type": "command"
Runs a shell command in the project's working directory. The exit code controls whether the triggering action proceeds (see Exit Codes below). Environment variables such as $FILE_PATH, $TOOL_NAME, and $COMMAND are injected automatically.
"type": "prompt"
Injects additional text directly into the LLM's context. Use this to prepend instructions, warnings, or dynamic data into the model's input — for example, injecting the current git branch name or a security policy reminder before every agent response.

Exit Codes

When using "type": "command", the shell exit code determines what happens next:

Exit Code Meaning Effect
0 Success The triggering action proceeds normally (fail-open)
2 Block The action is PREVENTED — fail-closed
Any other Failure Hook failed, but the action proceeds anyway (fail-open)
Fail-Closed Exceptions: beforeReadFile and beforeMCPExecution are fail-closed by default — if the hook command fails for any reason (not just exit 2), the read or MCP call is blocked. Design hooks for these events with extra care.

7.5 Configuration Levels

Hooks can be defined at four levels. When the same lifecycle event has hooks at multiple levels, they are merged and run in priority order — highest priority first:

  1. Enterprise — highest priority; cannot be overridden by lower levels
  2. Team
  3. Project (.cursor/hooks.json in the repo)
  4. User — lowest priority (personal machine settings)

Enterprise hooks are locked — team, project, and user hooks cannot override or disable them. This makes enterprise hooks suitable for enforcing security policies across all developers.

8.3 Common Pitfalls in Real Environments

Corporate proxies and TLS

MCP servers, /research, and any external doc fetch will hit your corporate proxy. Set HTTPS_PROXY / NO_PROXY in your shell, and if your org uses an internal CA, configure NODE_EXTRA_CA_CERTS for Cursor and SSL_CERT_FILE for Python tooling. Symptom: silent failures on the first MCP call.

Auth: SSO, MFA, and short-lived tokens

Cursor and Claude Code authenticate independently. SSO works, but MFA prompts can stall a long-running agent. For team environments, configure CLI auth using a refresh-friendly token method (e.g. aws sso login before the session, not during).

Team CLAUDE.md conventions

If your team already commits a CLAUDE.md, do not overwrite it. Append your ## Active Persona and ## Active Stack sections under the existing header, and put personal preferences in ~/.claude/CLAUDE.md (user-global) instead of the project file.

Strictness mismatch on legacy code

The most common “the AI fights me” complaint comes from running High strictness on a brownfield codebase. Symptom: every /code-review returns 30+ blockers. Fix: set Strictness: Low for the legacy paths and Strictness: High only for the app/v2/ (or equivalent) new tree.

Secret leakage

Never commit .env, credentials, or live API keys. Add a hook that blocks git add if the staged diff matches secret patterns. The template ships an example under .claude/hooks/.
