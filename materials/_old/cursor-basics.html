0. Orientation & Mental Model

What do I get from this section?

By the end of this section you will know why Cursor exists, what changes when AI sits inside your editor, and the one mental shift you must make to use it well.

Before: “The AI is autocomplete on steroids. I type, it guesses the next few characters.”
After: “The AI is a context-aware pair programmer. The quality of its output is a function of the context I give it. My job is to curate context, not to write prose.”

⏱ 10 min — Instructor framing

Why AI-assisted development matters now

Three things changed in the last 18 months: long context windows (200k+ tokens) made whole-project reasoning practical; tool-use APIs let models act (read files, run tests, open PRs), not just suggest; and editors like Cursor finally exposed those capabilities in a workflow that respects how engineers actually think. The result is not “type less code.” It is change the unit of work from “line of code” to “intent + acceptance criteria.”

The one mental-model shift

Most people fail at AI-assisted development because they treat the model as a magic autocomplete and judge it by its first answer. Strong users treat it as a context-bound junior engineer: brilliant when the brief is sharp, mediocre when the brief is vague. Three habits separate the two groups.

  • Curate context, don’t paste it. Use @ symbols and rules so the model sees exactly the right slice of the project.
  • Specify outputs, not steps. “Add tests for the empty list case” beats “use pytest fixtures and parametrize.”
  • Iterate in small loops. Generate → review → correct → commit. Never accept a 600-line diff blindly.
The AI is only as good as the context you give it. The whole rest of this course is about building, loading, and reusing that context.

1. What is Cursor?

What do I get from this section?

You will be able to explain what Cursor is, why it is not just “VS Code with a chatbot,” and what architectural pieces (Rules, Commands, MCP) make AI behave consistently across a session.

Before: “I have Copilot in VS Code; isn’t that the same thing?”
After: “Copilot completes lines. Cursor runs commands across files, reads my project rules, and edits a feature end to end.”

⏱ 10 min — Demo

Cursor is an AI-first code editor built as a fork of Visual Studio Code. It is fully VS Code under the hood — your extensions, keybindings, settings, and terminal all transfer — and on top of that base it adds first-class AI: completions, an Agent that edits multiple files, a context engine that reads project rules, and a slash-command system you can extend.

Mental shortcut: VS Code + a senior pair programmer who has read your whole repo and remembers your team’s conventions.

Slash commands None Custom commands in .cursor/commands/

Under the hood

Cursor sits between you and the LLM. Your prompts get enriched with project context (rules, open files, @-attached references) before being sent to the model. The model’s response is parsed back into edits, terminal commands, or chat replies.

2. The 4 AI Interfaces

What do I get from this section?

You will know which of the four AI surfaces to reach for in any given moment, and stop wasting time using the wrong one.

Before: “I open Chat for everything — even renaming a variable.”
After: “Tiny edit → Tab. Targeted edit → Cmd+K. Question → Chat. Whole feature → Agent.”

Tab Completion

Situation: You are mid-flow typing code you already know how to write.

Task: Get the next few lines without breaking concentration.

Action: Start typing. Cursor shows a grey ghost-text prediction. Press Tab to accept, Esc to dismiss.

Result: Boilerplate disappears. You spend keystrokes only on intent.

ActionShortcutWhat happens
Accept full suggestionTabInserts the entire ghost-text block
Accept one wordCtrl+→Walk through the suggestion word by word
RejectEscDismisses the ghost text
Jump to next predicted editTab after acceptCursor moves to the next likely edit spot

Best for: variable names, repetitive patterns, finishing a function body you already see in your head.

Inline Edit (Cmd+K)

Situation: You see a block of code that needs a targeted change — add validation, convert to async, rename for clarity.

Task: Edit just that region without leaving the editor.

Action: Select the lines. Press Cmd+K (Mac) / Ctrl+K (Win/Linux). A small prompt opens inline. Describe the change. Hit Enter. Review the diff. Accept or reject.

Result: The selection is rewritten. Nothing else moves.

Good prompts:

  • “Add input validation: reject empty list, reject non-numeric values”
  • “Convert this function to async/await”
  • “Add Google-style docstring with Args, Returns, Raises”

Common mistake: using Cmd+K when the change spans multiple files. Use Agent instead.

Chat Panel (Cmd+L)

Situation: You don’t want code yet. You want to understand something or plan.

Task: Ask the model a question and reference files for context.

Action: Press Cmd+L — the chat panel opens on the right. Type your question, attach files with @filename, send.

Result: An answer in the panel. Your code is never touched.

Good prompts:

  • “Explain how @app/core/database.py manages connection pooling.”
  • “Why does this test fail? (paste error)”
  • “What would be the smallest change to add caching to the posts endpoint? Don’t write code yet.”

Agent / Composer Mode (Cmd+I)

Situation: You have a feature, refactor, or scaffolding job that touches multiple files.

Task: Let the AI plan, edit, run, and iterate — with you in the loop reviewing diffs.

Action: Press Cmd+I. Describe the goal. Watch Agent read files, propose edits, optionally run terminal commands.

Result: A coherent multi-file change you review and accept piece by piece.

Agent can:

  • Create, edit, and delete multiple files
  • Run terminal commands (build, tests, lint) and read the output
  • Read your .cursor/rules/*.mdc automatically and follow them
  • Invoke slash commands (@set-persona, @architect, etc.)
  • Iterate on failures: if a test fails it reads the output and fixes the code
  • Use MCP tools (DBs, APIs, docs) when configured
Agent is where the structured workflow lives

For the rest of this course, almost everything happens in Agent mode. Tab and Cmd+K are for tactical edits. Agent is for building — following rules, running commands, producing reviewable diffs.

3. The Context System

What do I get from this section?

You will know how to feed the AI exactly the right files and information — the difference between a vague answer and a precise one.

Before: “The AI hallucinated a function name that doesn’t exist.”
After: “I attached the actual file with @app/services/user.py — the AI used the real signature.”

⏱ 10 min — Demo

The quality of AI output is bounded by the context it sees. Cursor uses @ symbols to attach specific context to any prompt. Treat @ as the most important keyboard habit you build today.

@ Symbol Reference

SymbolWhat it attachesExample
@fileFull contents of a file@app/api/posts.py
@folderFile tree of a directory@app/modules/
@codebaseSemantic search over the whole repo@codebase how is auth handled?
@webLive web search results@web FastAPI dependency injection
@docsCrawled documentation from a URL@docs https://fastapi.tiangolo.com
@gitGit diff, commits, or PR context@git diff HEAD~3
@ is for context. @command is for commands.

@app/api/posts.py — “include this file in context.”
@start-session — “run this slash command.”

Same key, different meaning depending on whether the target is a file path or a command name. Claude Code uses /start-session for the same thing — this guide shows both.

How context flows to the AI

When you send a message, Cursor assembles a layered package: project rules, the context file, anything you attached with @, and your prompt itself. That whole package is what the model actually sees.

LLM R --> LLM CTX --> LLM F --> LLM style P fill:#ff9800,color:#fff style LLM fill:#2e7d32,color:#fff style R fill:#00897b,color:#fff -->

This is why rules and context files are so powerful — they are injected into every prompt, automatically. You set them up once and benefit for the rest of the session.

Context budget

Models have a finite context window. Attaching ten huge files dilutes attention. Pick the 2–3 most relevant. Use @codebase when you need a project-wide search, @file for surgical references.

4. The 3-Step Onboarding

What do I get from this section?

You will configure your project in three commands so the AI knows your role, your stack, and your conventions for the entire session — not just one prompt.

Before: Every prompt re-explains: “I’m a backend engineer using FastAPI with snake_case and pytest…”
After: One run of @set-persona → @setup-stack → @start-session and the AI already knows everything for the rest of the day.

⏱ 15 min — Demo

Why personas and stacks exist

Without onboarding, the AI is a generalist. It might suggest camelCase in a Python project, write Mocha tests for a Pytest codebase, or recommend Express patterns inside a NestJS app. The fix is not longer prompts — it is persistent context: rules and a context file the AI loads automatically.

The course pre-builds those rules and context per role + tech, so configuring is three commands instead of writing them yourself.

Step 1: @set-persona

What it does: installs the rules, commands, and agents for one role into .cursor/ and .claude/.

When to use: first thing in any new project, or any time you switch roles.

How to invoke: in Agent mode (Cmd+I) type @set-persona and press Enter.

The four personas:

designer UI/UX designers Token validation, component-spec templates, Figma context loader

data-scientist Data scientists / ML engineers Notebook + pipeline stacks, reproducibility-checker, experiment-tracker

What it does: installs the stack-specific rules and a context.md file that pins your language, framework, testing tool, and architecture shape.

When to use: right after @set-persona, unless your persona is pm or designer (skip).

How to invoke: @setup-stack — you’ll see only the stacks valid for your persona.

Step 3: @start-session

What it does: reads persona + stack + active phase, prints a status line, and asks for your session goal. From this point every Agent prompt is enriched automatically.

When to use: at the start of every working session — not just the first one.

How to invoke: @start-session.

Common mistake: skipping @start-session and going straight to coding. Without it, the rules and context aren’t guaranteed to be in scope — subtle drift creeps back in.

Lab 1 — Onboard a Fresh Project

⏱ 35 min — Lab ⏱ 5 min — Debrief

Lab 1: Three commands, working context

Goal: end with a project where typing one Agent prompt produces stack-correct code without further explanation.

Prerequisites:

  • Cursor installed (cursor.sh)
  • The course template cloned: git clone <course-repo> cursor-lab1 && cd cursor-lab1
  • Open the folder: cursor .

Steps:

  1. Open Agent (Cmd+I).
  2. Type @set-persona → Enter. Pick engineer (or your role).
  3. When the persona summary prints, run @setup-stack. Pick python-fastapi (or node-express / go-gin).
  4. Run @start-session. When asked the goal, answer: “Just verifying context is loaded; no code change yet.”
  5. Open .cursor/context.md and read it. Note Active Persona, Active Stack, Architecture Shape, Active Phase.
  6. List .cursor/rules/. You should see style.mdc, testing.mdc, etc.
  7. In Agent, type: “Without writing code, summarise the architecture pattern, naming convention, and test framework you would use for any new feature in this repo.”

Acceptance criteria — you are done when:

  • Step 5 shows your stack and persona populated (not placeholders).
  • Step 6 shows at least 2 .mdc rule files installed.
  • Step 7 reply names your stack’s exact framework, naming convention, and test tool — matching context.md. The AI did not ask you what stack you use.

If it fails:

  • “No persona configured” → you skipped step 2; run @set-persona.
  • AI still asks “what language?” → you skipped @start-session; rules aren’t loaded.
  • Wrong stack appears in context.md → rerun @setup-stack and pick again.
Extension — switch persona cleanly

⏱ 20 min — Extension

Re-run @set-persona and pick a different role (e.g. data-scientist, then python-datascience). Then switch back to engineer.

Acceptance:

  • Inspect .cursor/.persona-manifest.json — the file is rewritten each time.
  • The previous persona’s commands and rules are removed (no leftover files).
  • context.md updates Active Persona and Active Stack to the new selection.
  • No code in your project (e.g. app/ or src/) was touched. Only configuration changed.

5. @architect — Phase 0 Scaffolding

What do I get from this section?

One command turns a one-line idea (or a plan doc) into a runnable walking skeleton plus a sequence of session plans you can implement one at a time.

Before: “I have an idea. Now I spend an afternoon scaffolding folders, routes, models, and stub responses.”
After: “@architect "Build a blog API" — 90 seconds later I have a runnable skeleton and four numbered session plans in plan/sessions/.”

⏱ 10 min — Demo

What it does: Phase 0 of the development lifecycle. @architect reads your active stack, designs the interface (routes, pipeline stages, modules — depending on Architecture Shape), creates stub implementations that run, and writes per-feature session plans.

Two modes:

  • Design mode: @architect "Build a task management API" — the AI proposes the design.
  • Plan-extraction mode: @architect plan.md — the AI uses your plan as-is, no re-design.

When to use: at the very start of a feature, after onboarding, before you write any production code.

Expected output (annotated):

✅ Interface designed (7 endpoints — per Architecture Shape)
✅ 4 phases identified
✅ Session plans created in plan/sessions/
   - session-1-phase-0.md   # Skeleton
   - session-2-phase-1.md   # Posts CRUD
   - session-3-phase-2.md   # Comments
   - session-4-phase-3.md   # Auth
✅ Skeleton implemented:
   - app/api/posts.py (stub responses)
   - app/api/comments.py (stub responses)
   - app/main.py
   - tests/api/test_posts.py (smoke test)

Next: Run @start-session to begin implementation

Common mistake: running @architect before @setup-stack. The shape is unknown so the output is generic. Always onboard first.

The shape determines the output

Same command, very different deliverables: a REST stack produces routes + models, a Spark stack produces job stages + schemas, a Terraform stack produces modules + resource maps. The Architecture Shape (set during @setup-stack) drives this.

Lab 2 — Architect a Real Feature

⏱ 40 min — Lab ⏱ 5 min — Debrief

Lab 2: From idea to runnable skeleton

Goal: turn a one-sentence idea into a running app with stub endpoints and a phase plan.

Prerequisites: Lab 1 complete. .cursor/context.md shows engineer + python-fastapi (or your equivalent).

Steps:

  1. In Agent (Cmd+I), type: 
    @architect "Build a notes API with notebooks, notes, and tags. A notebook has many notes. A note can have many tags."
  2. Read the proposed design before approving anything. Confirm endpoints exist for: list notebooks, create notebook, list notes in notebook, create note, list tags, attach tag to note.
  3. Let the AI generate files. Watch the diff for each.
  4. Open plan/sessions/ and skim every session file.
  5. Run the skeleton (Python FastAPI example): 
    python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --reload
  6. Open http://localhost:8000/docs. You should see the auto-generated OpenAPI page with all endpoints listed.
  7. Hit one stub endpoint with curl: curl http://localhost:8000/notebooks. Expect a 200 with a stub body.

Acceptance criteria — you are done when:

  • The app starts without errors.
  • /docs shows at least 6 endpoints.
  • Each endpoint returns 200 with a stub payload (no real DB yet).
  • plan/sessions/ has at least 3 session files, numbered, each scoped to one feature.

If it fails:

  • ImportError on startup → check requirements.txt was installed inside the venv.
  • 404 on /docs → FastAPI app not mounted; reread app/main.py.
  • No plan/sessions/ directory → rerun @architect; it may have stopped at the design step.
Extension — plan-extraction mode

⏱ 20 min — Extension

Create plan.md by hand with three sections (Goals, Endpoints, Data Model). Be opinionated — specify a non-obvious choice (e.g. “use UUIDs not auto-incrementing ints”).

Run @architect plan.md. Acceptance:

  • Generated models use UUIDs (the AI honoured your spec).
  • The AI did not invent endpoints you didn’t list.
  • If your plan was unclear about something (e.g. auth), the AI asked rather than assumed.

6. The Session Loop

What do I get from this section?

You will know the full daily rhythm of AI-assisted work — not just “ask the AI to write code,” but a repeatable cycle that produces clean, reviewed, committed work.

Before: “I prompt, accept the diff, hope it works, paste errors back.”
After: “@start-session → goal → code → @code-review → commit → @next-session. Same loop, every day.”

⏱ 10 min — Demo

The loop is six steps. Each one is small. The discipline of running them in order is what turns AI from a toy into a workflow.

B["state goal"] B --> C["code with Agent"] C --> D["code-review"] D --> E["git commit"] E --> F["next-session"] F --> A -->

@code-review

What it does: runs a security + style + testing audit using your stack’s rules. Produces a list of violations with file references.

When to use: after every meaningful change set, before you commit.

How to invoke: @code-review — no args needed; it reads the diff.

Expected output (annotated):

Code Review — python-fastapi (Standard strictness)

❌ Security: app/api/posts.py:42 — raw f-string in SQL query (SQL injection risk)
⚠️ Style: app/services/post.py:18 — missing type hint on return value
✅ Testing: tests/api/test_posts.py covers create, list, get; missing 404 case

3 issues found.

Common mistake: committing without running @code-review. The model is fast at writing code and slow at thinking about edge cases — this command catches what was missed.

@next-session

What it does: writes a transition note — what was done, what’s next, which files to load next time. Optionally advances Active Phase in context.md.

When to use: at the very end of every working block, before closing the editor.

How to invoke: @next-session.

Expected output (annotated):

# Session Transition
**Last Status**: Success (12 tests passing)
**Stopped At**: app/services/post.py — pagination not yet implemented
**Next Step**: Add pagination to GET /posts (limit, offset query params)

**Context to Load**:
- @.cursor/context.md
- @app/services/post.py
- @plan/sessions/session-3-phase-2.md

Common mistake: ending a session without running it. Tomorrow you’ll re-explain everything to the AI — defeating the entire point of persistent context.

Lab 3 — One Full Session, End to End

⏱ 45 min — Lab ⏱ 10 min — Debrief

Lab 3: Implement one feature with the full loop

Goal: take Phase 1 of the skeleton from Lab 2 to a real, tested, reviewed, committed implementation — using all six loop steps.

Prerequisites: Lab 2 complete; skeleton runs; plan/sessions/session-2-phase-1.md exists.

Steps:

  1. Start. @start-session. When asked, answer: “Implement Phase 1 from session-2-phase-1.md — full CRUD for notebooks with tests.”
  2. Build. In Agent: “Implement the notebook CRUD per @plan/sessions/session-2-phase-1.md. Write the tests first (TDD), then the implementation. Run pytest after each file.”
  3. Review every diff before accepting. Reject anything you don’t understand and ask the AI to explain it.
  4. Verify. Run the tests yourself: pytest -q. Hit the endpoints with curl. Confirm green.
  5. Review. Run @code-review. Read every issue. Fix or justify each one (Cmd+K is great here).
  6. Commit. git add . && git commit -m "Phase 1: notebooks CRUD with tests".
  7. Wrap. @next-session. Save the transition block somewhere obvious (top of plan/sessions/session-3-phase-2.md, or a sticky note).

Acceptance criteria — you are done when:

  • pytest is fully green.
  • All four CRUD endpoints work via curl.
  • @code-review reports zero high-severity issues.
  • You have one commit on a feature branch.
  • The @next-session transition block exists and clearly names the next step.

If it fails:

  • Tests fail in obscure ways → paste the failure into Chat (Cmd+L) with @ attaching the failing test file. Don’t guess.
  • code-review flags “raw SQL” → let the AI fix it with parameterised queries; never silence security findings.
  • Agent makes giant unrelated edits → reject the diff, scope your prompt to one file with @.
Extension — resume from yesterday’s transition

⏱ 20 min — Extension

Close Cursor. Reopen the project. Start a brand-new chat (no history).

Paste your saved @next-session transition block as the first message and run @start-session. Implement Phase 2 (notes CRUD).

Acceptance: the AI picks up exactly where you left off. You did not re-explain the project to it.

What to customise

  • .cursor/context.md — your real project name, your real architecture pattern, current phase. Edit by hand any time.
  • .cursor/rules/*.mdc — add your company’s style rules (e.g. “all SQL must use parameterised queries”, “no console.log in production code”). Prefix client-specific rules with 900-client- so they sort after the base rules.
  • .cursor/commands/ — copy any of the existing .md files and edit. A new file there is a new slash command.
  • vibe/ — design or tone documents the AI will respect. Useful for product-voice consistency.

Common pitfalls in real environments

Read this before installing at work
  • Corporate proxy / TLS interception. Cursor needs HTTPS to the model provider. If your laptop has a custom root CA, set NODE_EXTRA_CA_CERTS in your shell so requests don’t fail with cert errors.
  • SSO / login loop. Some VPNs block Cursor’s login redirect; toggle the VPN off briefly during first sign-in, then back on.
  • Code privacy. Check your team’s policy. Cursor offers a Privacy Mode that doesn’t retain your code — required by many enterprises. Settings → Privacy.
  • Monorepos. The context engine indexes the whole repo by default. In huge monorepos, narrow the workspace to one package, or add .cursorignore to exclude vendored or generated code.
  • Team rules drift. Commit .cursor/rules/ and .cursor/context.md to your repo. The whole team benefits from the same context.
  • MCP credentials. If your persona pulls in MCP servers (Jira, GitHub, DBs), the install prints which env vars to set. Put them in .env, not in shell rc files committed to git.
