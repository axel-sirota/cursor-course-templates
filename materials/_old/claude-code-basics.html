0. How to Use This Guide

What do I get from this section?

You walk away knowing the rhythm of the day so you can pace yourself and not get lost.

BeforeAfter

1. What is Claude Code?

What do I get from this section?

You learn the one distinction that explains every other choice in this course: Claude Code is a CLI agent, not a chat window.

BeforeAfter
You think of Claude as something you paste code into and copy answers out of. You see Claude as a process running in your terminal that reads your repo, edits files, runs tests, and commits — while you stay in your editor of choice.

Situation — the pain Claude Code solves

You open ChatGPT or Claude.ai. You paste 200 lines of auth.py. You ask “refactor this.” You copy the answer back. You realize the AI hallucinated an import. You re-paste. Repeat 30 times a day. Your context lives in a chat tab; your code lives in your editor; the two never meet.

Task — what Claude Code is

Claude Code is Anthropic’s official agentic coding CLI. You run claude in any project directory and a conversational agent boots up inside the project. It reads files using its Read tool, edits with Edit/Write, runs shell commands via Bash, searches with Grep/Glob, and follows instructions you give it in plain English.

Mental model: a senior pair programmer that lives in your terminal, can see your entire project, executes changes autonomously, and never forgets the project rules — while you keep using Vim, VS Code, JetBrains, or Emacs.

CLI vs IDE-based AI — why this distinction matters

Capability GitHub Copilot Cursor IDE Claude Code
Interface IDE extension Forked VS Code editor Terminal CLI (any editor)
Editor lock-in VS Code / JetBrains Must use Cursor None — Vim, VS Code, Emacs, anything
Multi-file editing Limited Agent mode Native — always multi-file
Runs your tests No Yes, in chat Yes — is the terminal
Scriptability None Limited Unix pipes, CI, headless
Project rules Not supported .cursor/rules/*.mdc CLAUDE.md + .claude/rules/

Under the hood — the agentic loop

You ask. Claude plans. Claude calls a tool (read a file, run a test, edit code). Claude reads the result. Claude calls another tool. Loop until the goal is reached or it asks you a question. This is not autocomplete — it is a multi-step agent that uses tools.

CC TERM --> TOOLS TOOLS --> CTX CTX --> LLM["Claude Model
Anthropic API"] LLM --> TOOLS -->

Result — what you can now do

  • Stay in your editor; let Claude do the cross-file edits.
  • Pipe logs and CSVs into Claude with one command.
  • Script Claude into CI to triage commits or generate release notes.
Key insight — Unix philosophy

Claude Code is composable, scriptable, editor-agnostic. It integrates with your existing workflow through pipes, flags, and config files — not by replacing your editor. If you can write a shell pipeline, you can drop Claude into it.

2. The 3 Interaction Patterns

What do I get from this section?

You learn the three ways to invoke Claude Code, and when to pick each one.

BeforeAfter
You only know the chat-style interactive prompt and copy/paste data into it. You know to cat error.log | claude -p for triage, claude -p for one-shot questions in scripts, and claude for real building — and you stop using the wrong mode for the wrong job.

Situation

Different tasks need different shapes of conversation. A 6-step refactor needs back-and-forth. Triaging a 5MB log file needs one transformation pass. A CI hook needs a single answer with no follow-up. One tool, three modes.

2.1 Interactive Mode — claude

Task: drive a full agentic conversation. Claude reads, edits, runs tests, you correct it, it iterates. Stays alive until you exit.

cd my-project
claude

Inside the session, you can:

  • Type natural-language requests.
  • Use slash commands: /help, /init, /clear, /compact, /cost.
  • Reference files with @path/to/file.py.
  • Approve or deny each tool call (default permission mode).

Best for: building features, TDD cycles, multi-file refactors, debugging complex issues — anything that needs back-and-forth.

2.2 Headless Mode — claude -p

Task: ask one thing, get one answer, exit. No conversation, no follow-up, no TTY. Designed for scripts and CI.

# Quick question
claude -p "What testing framework does this project use?"

# Structured output for piping into jq
claude -p "List all FastAPI endpoints" --output-format json

# CI snippet: comment on PR if tests are missing
claude -p "Review the last commit. Output PASS or FAIL only."

Best for: CI/CD steps, git hooks, scripts, “hey, what was…” questions where you do not want to start a session.

2.3 Pipe Mode — stdin | claude -p

Task: feed data on stdin, get transformed output on stdout. Pure Unix.

# Explain a file
cat src/auth.py | claude -p "Explain this authentication flow"

# Add type hints (Claude returns code on stdout)
cat utils.py | claude -p "Add type hints. Output Python code only." > utils.typed.py

# Triage error logs
tail -200 /var/log/app.log | claude -p "Top 3 errors and root causes"

# Transform CSV to JSON
cat data.csv | claude -p "Convert to JSON array, no commentary" > data.json

Best for: log analysis, file transformation, batch explanation, format conversion. The output is data, not chat.

A 4th option: IDE extensions

Claude Code also has VS Code and JetBrains extensions that surface the same CLI agent in a sidebar with visual diff review. Same engine, same CLAUDE.md, prettier UI. Install from your IDE’s marketplace.

Permissions matter in the terminal

Unlike an IDE where actions are visual, Claude Code runs real commands. By default it asks before editing files or running shell commands. Configure with --permission-mode:

  • default — asks before risky operations (recommended).
  • plan — read-only mode. Cannot edit or run commands.
  • full-auto — no prompts. Use only on throwaway repos.

Common mistake: enabling full-auto on your main branch and waking up to a force-push.

Common mistake

Using interactive mode for a one-shot query, then leaving the session open all day burning context tokens. If your question fits in one prompt and one answer, use -p.

3. The Context System — CLAUDE.md is the AI’s Brain

What do I get from this section?

You learn the one file (CLAUDE.md) that turns Claude from a generic assistant into your project’s assistant.

BeforeAfter
You paste your project description (“we use FastAPI, snake_case, pytest…”) at the top of every conversation. One CLAUDE.md at the repo root loads automatically every session. The AI knows your stack, conventions, and active phase from the first message.

Situation

The quality of AI output is bounded by context. A model that does not know you use snake_case will write camelCase. A model that does not know you use Pytest will suggest unittest. Re-explaining your project on every prompt is exhausting and brittle.

Task — CLAUDE.md

A CLAUDE.md at your project root is loaded automatically at the start of every session. It tells Claude your stack, standards, build commands, and current phase.

# Project Context

## Active Persona
engineer

## Active Stack
python-fastapi

## Architecture Shape
REST API - FastAPI async endpoints, SQLAlchemy 2.0, Alembic, Pydantic v2.

## Active Phase
Phase 0 (Skeleton)

## Tech Stack
- Language: Python 3.11+
- Framework: FastAPI
- Database: PostgreSQL (SQLAlchemy 2.0+ async)
- Testing: Pytest

## Build & Run
- Install: pip install -r requirements.txt
- Run: uvicorn main:app --reload
- Test: pytest tests/ -v

## Code Standards
- snake_case for variables/functions, PascalCase for classes
- All endpoints must have type hints
- Use Pydantic models for validation
- No business logic in route handlers

Generate one automatically:

# Inside an interactive session
/init
CLAUDE.md is to Claude Code what .cursor/rules is to Cursor

If you came from Cursor: CLAUDE.md is the equivalent of .cursor/rules/*.mdc with alwaysApply: true. Always loaded, always enforced. For path-scoped rules, use .claude/rules/*.md.

Context sourceHow it’s loadedCursor equivalent
CLAUDE.mdAuto at session start.cursor/rules/*.mdc (alwaysApply)
.claude/rules/Path-scoped, loads when matching files are touched.cursor/rules/*.mdc (glob-attached)
.claude/commands/*.mdOn-demand via slash commands.cursor/commands/*.md
File readsClaude uses Read tool autonomously@file mentions
Code searchClaude uses Grep/Glob autonomously@codebase

Action — how context flows on every message

When you type a message, Claude Code assembles a rich package before calling the model. Unlike Cursor where you manually attach files with @, Claude Code discovers context autonomously.

LLM R --> LLM RULES --> LLM F --> LLM G --> LLM -->

Result

The model sees: your CLAUDE.md, the matching rules, files Claude has read, and your message — together, in one shot. That is why CLAUDE.md is so powerful: it is silently injected on every prompt.

Essential built-in slash commands
  • /help — show available commands
  • /init — generate or improve your CLAUDE.md
  • /clear — clear conversation, reset context
  • /compact — summarise the conversation to free tokens
  • /cost — show token usage and cost so far
  • /model — switch between Sonnet and Opus mid-session

4. Persona & Stack Onboarding

What do I get from this section?

You learn the 3-command flow that turns a fresh repo into a fully-configured AI workspace: persona, stack, session.

BeforeAfter
You write a CLAUDE.md by hand for every project, copy-paste the same standards, and forget to mention testing rules. Three slash commands install a curated persona pack, a stack rules library, and a working CLAUDE.md — in under 60 seconds.

Situation — the pain without it

Every new project: you spend 30 minutes typing out tech stack, naming conventions, testing strategy, build commands. You forget half of them. Two weeks in, the AI is still suggesting npm test in your Python repo because nobody told it. Multiply by every project, every team member.

Task — the three-step flow

/set-persona      # Step 1 - pick your role
/setup-stack      # Step 2 - pick a stack (filtered by persona)
/start-session    # Step 3 - load context and begin
P1[set-persona pick your role] P1 --> P2[setup-stack persona filtered stack list] P2 --> P3[start-session load context begin coding] P1 -.->|PM or Designer| P3 -->

Personas pm and designer skip /setup-stack — they have no tech stack. Engineers, DevOps, and data scientists run all three.

Action — the four personas and their stacks

/set-persona activates a persona pack: a curated set of slash commands, rules, and skills. /setup-stack is then persona-filtered, so you only see stacks that make sense for your role.

PersonaWho it’s forWhat it activates

data-scientist DS, ML, MLOps, data & analytics engineers Notebook-first /architect, experiment tracking, model card validation, reproducibility-checker subagent

Switching personas is safe

Re-run /set-persona at any time to switch roles. The previous persona’s files are removed cleanly via the manifest before the new one is installed. Your code is never touched — only the AI context changes.

Every stack declares an Architecture Shape in its context.md. /architect reads the shape and adapts its output accordingly.

5. Core Commands for Beginners

What do I get from this section?

You learn the six commands that cover 90% of a beginner’s day: configuration, design, build, review, wrap-up.

BeforeAfter
You know claude the binary but stare blankly when someone says “run /architect.” You can describe what each of the 6 core commands does, when to use it, and the most common mistake.
B[set-persona] B --> C[setup-stack] C --> D[start-session] D --> E[architect design] E --> F[code] F --> G[code-review] G --> H[next-session] H --> D -->

5.1 /set-persona

What: activate a persona pack (engineer, designer, pm, data-scientist). Installs commands, agents, hooks, rules into .claude/.

When: first thing on a new project, or whenever you change roles.

Invocation:

/set-persona
# → menu, pick number or name

Common mistake: running /setup-stack first — it will refuse, because no persona is set.

5.2 /setup-stack

What: pick a tech stack from a persona-filtered list. Copies stack rules, vibe guides, and templates. Writes Active Stack + Architecture Shape into CLAUDE.md.

When: right after /set-persona (engineers and data scientists only).

Invocation:

/setup-stack
# → persona-filtered menu, pick a stack

Expected output:

Stack configured: python-fastapi (REST API).
Run /start-session to begin your session.

Common mistake: picking a stack that does not match your real codebase. If you have an existing repo, run /detect-stack instead.

5.3 /start-session

What: load CLAUDE.md, active stack rules, and last-session summary. Asks for the goal of this session.

When: every time you sit down to work.

Invocation + expected output:

/start-session
Context Loaded: Python / FastAPI
Current Phase: Phase 0 (Skeleton)
Strictness: Default
What is the goal for this session?

Common mistake: skipping it and just typing “build me an API.” Claude technically has CLAUDE.md auto-loaded, but /start-session also surfaces the active phase and last-session beacon — which prevents repeating completed work.

5.4 /architect "Build X"

What: Phase 0 design. Produces interface contract (OpenAPI / route list / pipeline stages / module inputs) and a walking skeleton with stub responses, plus session plans in plan/sessions/.

When: at the start of every new feature or project, before you write any real code.

Invocation:

/architect "Build a task management API with users, tasks, and due dates"
# or with an existing plan:
/architect plan.md

Annotated expected output:

[1] Interface designed (8 endpoints):
    POST /users, GET /users/{id}, POST /tasks, GET /tasks, …
[2] 4 phases identified
[3] Session plans created in plan/sessions/
    - session-1-phase-0.md  (skeleton)
    - session-2-phase-1.md  (user CRUD)
    - session-3-phase-2.md  (task CRUD)
    - session-4-phase-3.md  (due-date logic)
[4] Skeleton implemented — main.py runs, all endpoints return 200 with stub data
Next: Run /start-session to begin implementation

Common mistake: jumping straight to feature code without /architect, then ending up with no test scaffolding and no phase plan.

5.5 /code-review

What: audit the codebase against the active stack’s rules — security (secrets, injection), style (naming, complexity), type safety, and test gaps. Persona-aware (different checks for designer vs PM vs data scientist).

When: before every commit, and any time you suspect drift.

Invocation:

/code-review

Expected output: a structured report with severity, file, line, finding, and suggested fix.

Common mistake: running it once and ignoring it. Treat it as a pre-commit hook in your head.

5.6 /next-session

What: wrap up. Summarises what changed, what tests pass, what is pending. Emits a copy-paste “Context Beacon” for next time.

When: end of every work session, before you close the terminal.

Invocation:

/next-session

Expected output:

# Session Transition
**Last Status**: Success
**Stopped At**: app/services/task_service.py::create_task
**Next Step**: Add validation for due_date > now() and write the failing test first.

**Context to Load**:
- CLAUDE.md
- app/services/task_service.py
- tests/api/test_tasks.py

Common mistake: closing the terminal without running it. Tomorrow’s you will have no idea where today’s you stopped.

6. The Session Loop — the Daily Rhythm

What do I get from this section?

You learn the repeatable 6-step cycle that turns Claude Code from “cool toy” into “the way we ship.”

BeforeAfter
You open Claude, vibe for 4 hours, lose track of what changed, forget to run tests, commit a mess. You follow start-session → goal → code → code-review → commit → next-session every time. Predictable, reviewable, resumable.

The cycle

B[state goal] B --> C[code with claude] C --> D[code-review] D --> E[commit] E --> F[next-session] F -.-> A -->
  1. /start-session — load context, see active phase, read last beacon.
  2. State the goal — one sentence. “Add due-date validation to POST /tasks.”
  3. Code with Claude — iterate. Let Claude propose, run tests, correct itself. Approve tool calls.
  4. /code-review — before committing, audit. Fix anything red.
  5. Commit — either via /commit built-in or your own git commit.
  6. /next-session — generate the transition beacon. Paste into your notes.
The loop is the product

The commands are easy to memorise. The discipline of running them in order is what produces a clean repo with reviewable diffs and resumable state. Skip /code-review twice and you accumulate drift; skip /next-session twice and tomorrow you replay yesterday’s work.

Lab 3 — The Review Loop

What do I get from this lab?

You run /code-review on the code from Lab 2, get real findings, and apply at least one fix — closing the build/review/commit loop.

⏱ 35 min — Lab Audit and fix

Prerequisites: Lab 2 done. The tasks API runs and returns 200.

Step 1 — Run review

  1. In your active Claude session, type /code-review.
  2. Wait for the audit report. Expect findings in at least one of: secret hygiene, type safety, test coverage, naming.
  3. Copy the report into plan/lab3-review.md (your evidence for acceptance).

Step 2 — Triage

  1. Pick the highest-severity finding.
  2. Ask Claude: “Fix only finding #1. Show me the diff before applying.”
  3. Approve the edit.
  4. Re-run pytest — tests must still pass.

Step 3 — Re-review

  1. Run /code-review again.
  2. Confirm the fixed finding no longer appears.

Step 4 — Wrap up

  1. Commit: git add . && git commit -m "fix: address code-review finding"
  2. Run /next-session. Save the transition beacon to plan/last-session.md.

Acceptance criteria — you’re done when:

  • plan/lab3-review.md contains the original audit report.
  • At least one finding is resolved (visible in git log -p).
  • The second /code-review run no longer flags that finding.
  • plan/last-session.md contains the transition beacon.
⏱ 20 min — Extension Make the review fail on purpose
  1. Hardcode a fake API key in app/config.py (e.g. API_KEY = "sk-1234567890abcdef").
  2. Run /code-review. Confirm it flags the secret as Critical.
  3. Move it to an environment variable and re-run review. Confirm it goes away.
  4. Bonus: add a .env.example with the variable name only.

7. CLAUDE.md Anatomy — Section by Section

What do I get from this section?

You can read any CLAUDE.md and predict what the AI will do, and you can edit yours with confidence.

BeforeAfter
You see CLAUDE.md as a magic file generated by /init that you do not touch. You know which sections drive which behaviors and you tune them on purpose.

The standard sections

SectionWhat it doesTouched by
## Active Persona Tells every command which preamble branch to follow (engineer / designer / pm / data-scientist). Missing → defaults to engineer. /set-persona
## Active Stack Names the stack so commands like /architect and /code-review load the right rules. /setup-stack
## Architecture Shape Drives the kind of skeleton /architect produces (REST API vs Data Pipeline vs IaC…). /setup-stack
## Active Phase Tells /start-session where you are (Phase 0 skeleton, Phase 1 first feature, etc.) so it can advance correctly. /setup-stack sets, /next-session advances
## Tech Stack Free-form description of language/framework/db/test tooling. Read by the model, not parsed. You, or /init
## Build & Run Exact shell commands Claude will use when you say “run the tests” or “start the app.” You, or /init
## Code Standards Naming conventions, type-hint rules, architectural pattern. Enforced by /code-review. Stack template, plus your edits
## Strictness Default / Low. Low is for legacy/brownfield: do not refactor what you do not touch. You
## Active Client (optional) Loads client-config overlays (extra rules, MCP servers, env-var requirements). /set-persona if client-config/ exists

Reading a real CLAUDE.md

# Project Context

## Active Persona
engineer                       # ← engineer preambles for /architect /code-review etc.

## Active Stack
python-fastapi                 # ← loads stacks/python-fastapi/rules into .claude/rules

## Architecture Shape
REST API - FastAPI async…     # ← /architect produces OpenAPI + walking skeleton

## Active Phase
Phase 0 (Skeleton)             # ← /start-session shows this; advances after Phase 0 AC met

## Strictness
Default                        # ← full standards on all code

## Build & Run
- Install: pip install -r requirements.txt
- Run: uvicorn main:app --reload
- Test: pytest tests/ -v       # ← Claude will literally run this when asked to test

## Code Standards
- snake_case for functions, PascalCase for classes
- Pydantic models for all request/response bodies
- No business logic in route handlers
Things that bite beginners
  • Out-of-date Build & Run commands — Claude will run exactly what is there, even if it is wrong.
  • Two CLAUDE.md files — one at repo root, one in ~/.claude/CLAUDE.md (your global). Both load. The global wins on conflicts.
  • Standards in prose, not bullets — the model reads bullets more reliably than long paragraphs. Be terse.

8. How to Adapt This After Class

What do I get from this section?

BeforeAfter
You go home buzzing but unsure what to do Monday morning beyond “install the CLI.” You have a 3-step ordered plan, role-specific advice, and a list of things to negotiate with your IT/security team.

Apply at work — per role

Software engineers

  • Pick one repo you own. Run /detect-stack to bootstrap a CLAUDE.md from existing code.
  • Set ## Strictness: Low if it is legacy.
  • Add /code-review to your pre-push muscle memory before adding it to CI.
  • Use claude -p in git hooks for commit-message linting.

Data scientists / ML engineers

  • Use python-datascience stack for notebooks, python-mlops for serving, python-spark for pipelines.
  • Pin every package in requirements.txt — the reproducibility-checker subagent will flag floating versions.
  • Keep seed set explicitly; the persona’s rules look for it.
  • Treat experiments like commits: one /start-session per hypothesis, one /next-session when the run finishes.

DevOps / platform engineers

  • Pick the right stack: devops-terraform for IaC, devops-ansible for config mgmt, devops-k8s-helm for Kubernetes.
  • Run Claude in --permission-mode plan against production-touching repos. Read-only is your friend.
  • Use pipe mode to triage CloudWatch / Stackdriver logs: aws logs tail … | claude -p "top errors".
  • Never put terraform apply in ## Build & Run — only terraform plan.

Product managers

  • No stack. Run /set-persona → pick pm → /start-session.
  • Use /architect on a product brief to get a PRD draft with goals/non-goals/INVEST stories.
  • Use /code-review on your PRD to get gap analysis (the gap-detector subagent flags missing NFRs).
  • Treat the AI as a junior PM that drafts; you edit.

Customise your CLAUDE.md / persona / stack

  • Repo-specific rules: add a ## Project Specific section to CLAUDE.md (e.g. “all monetary values in USD cents”).
  • Team-wide rules: commit CLAUDE.md and .claude/rules/ to git so every teammate gets the same AI behavior.
  • Custom commands: drop my-cmd.md into .claude/commands/ — it becomes /my-cmd instantly.
  • Custom stack: if your stack is not in the catalogue, copy stacks/python-fastapi/ as a template and adapt.

Common pitfalls in real environments

PitfallMitigation
Corporate proxy blocks api.anthropic.com Set HTTPS_PROXY and NO_PROXY. Use ANTHROPIC_BASE_URL if you have a Bedrock or Vertex gateway.
SSO / OAuth login fails over SSH Use API key auth: export ANTHROPIC_API_KEY=… in your shell init.
Team CLAUDE.md drift Commit it. Code-review it. Treat it like a config file, not a sticky note.
Secrets accidentally added to context Add .env, secrets/ to .claudeignore. Set --permission-mode plan when exploring unknown repos.
Large monorepo, slow context loads Scope CLAUDE.md per package. Use sub-CLAUDE.md files in subdirectories — Claude picks the nearest one up.
“It works for me” on personal laptop, not on shared dev box Pin the Claude Code version: npm install -g @anthropic-ai/claude-code@x.y.z.
