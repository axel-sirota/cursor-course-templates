1. Introduction

What is Claude Code?

Claude Code is Anthropic’s official agentic coding CLI. Unlike IDE-based AI tools, Claude Code runs in your terminal and works with any editor. You describe what you want in natural language, and it reads your codebase, edits files, runs commands, manages git, and calls external tools to get it done.

Aspect Cursor IDE Claude Code
Interface GUI — forked VS Code editor CLI-first — terminal + optional IDE extensions
Editor Lock-in Must use Cursor editor Works with any editor (VS Code, Vim, JetBrains, etc.)
Context System .cursor/rules/*.mdc with frontmatter CLAUDE.md files + .claude/rules/
Custom Commands .cursor/commands/*.md (invoked with @) .claude/skills/ (invoked with /slash)
Automation .cursor/hooks.json (Beta) .claude/settings.json hooks (production)
External Tools VS Code extensions MCP servers (Model Context Protocol)
Composability GUI-centric workflows Unix pipes, scripts, CI/CD integration
Parallelism Single session Git worktrees + subagents for parallel work

The Agentic Engineering Philosophy

Claude Code, like Cursor, is only as good as the context you give it — AI is context-hungry, and generic prompts produce generic code. Give it a clear technology stack (CLAUDE.md), explicit rules (.claude/rules/), a structured workflow (Phase-Based Development), and bounded sessions (/start-session → code → /next-session), and the code it produces follows your standards.

Write rules that are explicit and consistent, not clever.
Key Insight

Claude Code follows the Unix philosophy: it's a composable CLI tool that scripts into your existing pipes, flags, and configuration files. The more context you provide via CLAUDE.md and rules, the better it performs.

Plan Mode

Plan Mode is a read-only exploration mode where Claude analyzes your codebase and designs an implementation strategy before writing any code.

ActivateShift+Tab to toggle, or claude --permission-mode plan
Can doRead files, search code, ask questions, write plan files

Pro Tip

Use Plan Mode for multi-step features. Let Claude explore the codebase, design the approach, then exit Plan Mode and execute. This prevents wasted tokens on wrong approaches.

3. CLAUDE.md System

CLAUDE.md files are the backbone of Claude Code’s AI behavior. They are the equivalent of Cursor’s .cursor/rules/*.mdc system — persistent instructions that tell the AI how to write code for your specific project.

File Hierarchy

Claude Code loads instructions from multiple scopes, merged in priority order:

Real Example: Project CLAUDE.md

# Project: Blog API

## Tech Stack
- Language: Python 3.11+
- Framework: FastAPI
- Database: PostgreSQL (SQLAlchemy 2.0+ AsyncIO)
- Testing: Pytest (AsyncIO)
- Linting: Ruff
- Formatting: Black

## Build & Run
- Install: `.venv/bin/python3 -m pip install -r requirements.txt`
- Run: `.venv/bin/python3 -m uvicorn main:app --reload`
- Test: `.venv/bin/python3 -m pytest tests/ -v`
- Lint: `.venv/bin/python3 -m ruff check .`

## Code Standards
- Use snake_case for all Python identifiers
- All endpoints must have type hints and docstrings
- Use Pydantic models for request/response validation
- Never use `print()` — use `logging` module

## Architecture
- Modular structure: `app/modules/{name}/`
- Each module has: models/, services/, api/
- Repository pattern for database access

## Workflow
- Active Phase: Phase 0 (Skeleton)
- Strictness: High
- TDD is mandatory: write failing tests before implementation

## Common Patterns
See @docs/patterns.md for shared utilities
Imports with @

Use @path syntax to include other files by reference: @README, @docs/style-guide.md, @~/.claude/my-prefs.md. This keeps CLAUDE.md concise while linking to detailed docs.

Rules Directory: .claude/rules/

For more granular control, create topic-specific rule files in .claude/rules/. These can be path-scoped to only load when matching files are being edited. 

---
paths:
  - "app/api/**/*.py"
  - "tests/api/**/*.py"
---

# API Development Rules

## Endpoint Standards
- All endpoints MUST return Pydantic response models
- Use dependency injection for database sessions
- Include OpenAPI description in every route decorator

## Error Handling
- Use HTTPException with appropriate status codes
- Never expose internal error messages to clients
- Log all 500 errors with full traceback

Best Practices (same as Cursor rules)

Keep files under 200 lines. Large files dilute attention, so split into composable rules.

Be specific. “Use snake_case for variables” beats “follow Python conventions.”

Path-scope when possible. API rules shouldn’t load when editing Docker configs.

Composable over monolithic. Many focused files beat one giant CLAUDE.md.

Lab: Shape Your CLAUDE.md

Easy

Add one explicit, testable rule to your project’s CLAUDE.md, then prove — without mentioning the rule in your prompt — that Claude Code’s output honors it.

Hard

Add a ## Key Rules subsection with 2–3 explicit, checkable rules, then deliberately ask for something that conflicts with one of them. Claude Code should hold the line instead of silently complying.

Lab: Write a Custom Rule

Easy

Create an alwaysApply: true rule in .claude/rules/ that enforces a naming or style convention, and prove it fires on ordinary code generation.

Hard

Create a glob-scoped rule (alwaysApply: false + globs) that flags hardcoded secrets in your stack’s source files. Prove it fires on a matching file and stays silent on a non-matching one.

4. Skills & Slash Commands

Skills are Claude Code’s equivalent of Cursor’s custom commands. They live in .claude/skills/ directories and are invoked with the / prefix.

How Skills Work

When you type /start-session, Claude Code loads .claude/skills/start-session/SKILL.md and injects its content into the prompt. Any additional text you type after the command is passed as $ARGUMENTS.

5. Schema-Driven Development & TDD

This methodology combines Schema-Driven Development (SDD), designing the API contract first, and Test-Driven Development (TDD), writing tests before implementation. The steps are the same in Cursor and Claude Code; only the invocation syntax changes.

Schema-Driven Development (SDD)

SDD means you define the shape of your API before writing any code. The schema (OpenAPI spec) becomes the single source of truth.

SDD PrincipleWhat It MeansIn Practice
Contract First Design the API before implementing it /architect generates OpenAPI spec
Schema = Truth The spec defines what gets built Endpoints, models, and validation come from the spec
Mock First Skeleton returns fake data matching the schema Phase 0 creates all endpoints with mock responses
Validate Shape Verify the API structure before adding logic E2E tests run against mocks to prove the shape is right
Why Schema First?

When you tell the AI “build a blog API,” you might get 10 different designs. With SDD, you lock in the contract during /architect, and the AI follows that contract exactly during implementation, so the design doesn't drift between sessions.

async def test_create_post(client: AsyncClient, db_session):

# app/modules/posts/services/post_service.py

class PostService:
    def __init__(self, session: AsyncSession):
        self.repo = PostRepository(session)

    async def create(self, payload: PostCreate) -> Post:
        """Create a new blog post with validation."""
        await self._validate_author_exists(payload.author_id)
        post = Post(**payload.model_dump(), status="draft")
        return await self.repo.save(post)

    async def _validate_author_exists(self, author_id: int) -> None:
        """Raise 404 if author doesn't exist."""
        author = await self.author_repo.get(author_id)
        if not author:
            raise HTTPException(404, f"Author {author_id} not found")

The workflow combines Phase-Based Development, TDD, Bounded Sessions, and Context-First AI.

Phase 1+ — Implementation Implement one endpoint at a time using TDD. Real logic, passing tests, documented phase transitions

The Command Chain

Development follows a structured chain of slash commands:

/setup-stack → /architect → /start-session → (code) → /code-review → /next-session

Three Workflows

Workflow 1: Fresh Project with Known Stack

  1. Clone the template: git clone <repo>
  2. Open terminal: cd project && claude
  3. Configure stack: /setup-stack — choose your stack
  4. Design your feature: tell Claude /architect "Build a task management API"
  5. Start coding: /start-session

Workflow 2: Fresh Project with Custom Stack

  1. Clone the template
  2. Create CLAUDE.md with your stack details
  3. Create .claude/rules/ with custom rule files
  4. Optional: add skills in .claude/skills/
  5. Configure: /setup-stack
  6. Build: /architect → /start-session

Workflow 3: Existing Codebase (Brownfield)

  1. Navigate to your existing repo
  2. Run claude in the terminal
  3. Auto-detect: /detect-stack or /init
  4. Review generated CLAUDE.md, set Strictness to Low for legacy code
  5. Start working: /start-session

Lab: Run a Full Session

/code-review Is a Convention, Not a Gate

Nothing mechanically stops you from running /next-session right after a /code-review that found real issues — there is no severity field or pass/fail check wired between them. Treating “fix flagged issues before moving on” as a hard rule is your discipline to practice, not something the tooling enforces for you.

Easy

Pick any stack and, on a Blog API (Posts + Comments), run the full pipeline once end-to-end: /setup-stack → /architect → /start-session → implement one endpoint with TDD → /code-review → /next-session → /start-session. Deliverable: a plan/PHASES.md diff showing the phase advanced between your two /start-session runs.

Hard

Run the same pipeline on a different endpoint, but deliberately plant one real issue before /code-review (a hardcoded secret, a missing validation, an untested error path). Triage the free-text findings yourself, fix the blocking one, re-run /code-review to confirm it’s clean, and only then run /next-session. Deliverable: your before/after /code-review output plus the resulting plan/PHASES.md diff.

8. Hooks System

Hooks are lifecycle interceptors defined in .claude/settings.json. They run shell commands before or after specific AI actions, for example to format code, block dangerous operations, or inject context.

Configuration Format

Hooks are defined in the "hooks" key of your settings file:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write $(jq -r '.tool_input.file_path')"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/hooks/validate-bash.sh"
          }
        ]
      }
    ]
  }
}

Hook Types

TypeRunsUse Case
Command ("type": "command") Shell command Format code, run linters, block dangerous ops
HTTP ("type": "http") POST to URL Webhook notifications, external integrations
Prompt ("type": "prompt") Single LLM call[4] Quick validation, content checks
Agent ("type": "agent") Multi-turn subagent Complex verification workflows

Exit Codes

Exit CodeMeaningBehavior
0SuccessAction proceeds normally
2BlockAction is prevented (write reason to stderr)
OtherFailureFail-open: action proceeds anyway[5]

Any exit code other than 0 or 2 is treated as a non-blocking error and the action proceeds anyway (fails open) — except WorktreeCreate, where any non-zero exit code fails the worktree creation.

Configuration Levels

Hooks are merged in priority order:

Managed (Org) → Project (.claude/settings.json) → Local (.claude/settings.local.json) → User (~/.claude/settings.json)

Higher-priority hooks run first. Managed hooks cannot be overridden.

Real-World Examples

Auto-Format on File Edit

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{
          "type": "command",
          "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
        }]
      }
    ]
  }
}

Block Dangerous Shell Commands

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "if echo \"$TOOL_INPUT\" | grep -qE '(rm -rf|drop table|truncate)'; then echo 'BLOCKED by hook policy' >&2; exit 2; fi"
        }]
      }
    ]
  }
}

Desktop Notification When Claude Needs Attention

{
  "hooks": {
    "Notification": [
      {
        "matcher": "idle_prompt",
        "hooks": [{
          "type": "command",
          "command": "osascript -e 'display notification \"Claude Code needs you\" with title \"Claude Code\"'"
        }]
      }
    ]
  }
}

9. MCP Servers (Model Context Protocol)

MCP is Claude Code’s extension system, roughly equivalent to VS Code extensions for Cursor. MCP servers give Claude access to external tools such as databases, APIs, browsers, and web scrapers.

Configuration

MCP servers are defined in .mcp.json (project) or ~/.claude/mcp.json (user):

{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "uvx",
      "args": ["mcp-server-github"]
    },
    "postgres": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://user:pass@localhost/db"]
    },
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"]
    },
    "slack": {
      "type": "http",
      "url": "http://localhost:3000/mcp"
    }
  }
}

Configuration Scopes[6]

ScopeLocationShared?
Local~/.claude.json (keyed to the project path)No — personal, current project only (default)
Project.mcp.json at the project rootYes — team-shared via version control
User~/.claude.jsonNo — personal, all projects

10. Subagents & Worktrees

Subagents are specialized Claude instances that handle focused tasks with their own system prompts, tool access, and isolated contexts. Worktrees provide git-level isolation for parallel work.

Built-in Subagents

AgentPurposeModelTools
ExploreFast read-only codebase researchInherited (capped at Opus)[7]Read, Grep, Glob (no edits)
PlanPre-implementation design & architectureInheritedRead, Grep, Glob (no edits)
general-purposeComplex multi-step tasksInheritedAll tools

As of Claude Code v2.1.198, the built-in Explore subagent no longer runs on a fixed Haiku model — it inherits the main conversation’s model (capped at Opus on the Claude API). Prior versions defaulted Explore to Haiku; a user/project subagent named Explore can still be defined with model: haiku to force the lower-cost model.

Custom Agents

Define custom agents in .claude/agents/{name}/AGENT.md: 

---
name: code-reviewer
description: Expert code reviewer. Reviews code for quality, security, and maintainability.
tools: Read, Grep, Glob, Bash
model: sonnet
memory: project
---

You are a senior code reviewer. When invoked:

1. Analyze the recent changes with `git diff`
2. Review for: clarity, security, error handling, duplication, performance
3. Provide feedback organized by priority (critical, warnings, suggestions)
4. Include specific examples of how to fix issues

## Review Checklist
- [ ] No hardcoded secrets or credentials
- [ ] Error handling covers edge cases
- [ ] Functions have appropriate type hints
- [ ] Tests cover the new code paths
- [ ] No unused imports or dead code

Git Worktrees for Parallel Work

Worktrees create isolated copies of your repo so multiple Claude sessions can work in parallel without file conflicts. 

# Start Claude in a named worktree
claude --worktree feature-auth

# Auto-generated worktree name
claude --worktree

# Use /batch to auto-decompose into parallel worktree agents
/batch "Migrate all API endpoints from v1 to v2"
Parallel Development Pattern

Use /batch for large refactors. It decomposes the task into 5–30 parallel subtasks[8], each running in its own git worktree with a dedicated subagent. Each subtask opens its own pull request for human review — results are not merged back into your branch automatically[9].

12. Memory System

Claude Code has a persistent, file-based memory system that carries knowledge across sessions. Cursor IDE has no direct equivalent.

How It Works

FeatureDetails
Location~/.claude/projects/{project}/memory/[14]
IndexMEMORY.md — the first 200 lines, or the first 25KB (whichever comes first), loaded each session[15]
Topic filesIndividual .md files loaded on-demand
Auto-memoryClaude takes notes automatically when enabled
Browse/memory command to view and edit

Memory Types

TypePurposeExample
user User role, preferences, knowledge level “Senior Python dev, new to React frontend”
feedback Corrections and guidance from user “Don’t mock the database in integration tests”
project Ongoing work, goals, deadlines “Merge freeze starts 2026-03-05 for mobile release”
reference Pointers to external resources “Pipeline bugs tracked in Linear project INGEST”

Memory File Format

---
name: testing-preferences
description: How the team prefers to write and run tests
type: feedback
---

- Integration tests must hit a real database, never mocks
- Use pytest fixtures for database setup/teardown
- Run tests with: `.venv/bin/python3 -m pytest tests/ -v`
- Always test both happy path and error cases

- [testing-preferences.md](testing-preferences.md) - Testing approach and conventions

Enable Auto-Memory

Add to ~/.claude/settings.json: 

{
  "autoMemoryEnabled": true
}

Claude will automatically save important context across sessions, including build commands, debugging insights, and user preferences.

Ask Claude to Remember

You can explicitly ask: “Remember that we always use snake_case for database columns.” Claude will save it to the appropriate memory file. You can also say “Forget the thing about snake_case” to remove a memory.
