0. How to Use This Guide

What you walk away with from this guide

By the end of this one-day course you will have configured a real persona-aware Claude Code project, scaffolded a working endpoint or pipeline with /architect, and run the full start-session → code-review → next-session loop on a feature you can keep using on Monday.

Before: you re-explain your stack and conventions to the AI in every chat. After: two slash commands load all that context once, and the AI follows your rules for the whole session — across days, machines, and team members.

Every section in this guide follows the same rhythm:

  1. What you get — a one-paragraph payoff in a blue callout (always the first thing).
  2. Situation & Task — the real problem and what you will do about it.
  3. ⏱ 10–15 min — Demo — instructor types, students watch.
  4. ⏱ 30–45 min — Lab — students build the working artefact.
  5. ⏱ 15–20 min — Extension — for early finishers, harder, no hand-holding.
  6. ⏱ 5 min — Debrief — what we just learned, what to take to work.
Prerequisites

Claude Code installed and authenticated (claude --version), the cursor-course-templates repo cloned, and a terminal in that directory. If you are missing any of these, fix them now — we will not slow down for setup.

1. Introduction & Mental Model

What you get from this section

A clear mental model of why Claude Code exists and where it differs from generic chat AI — so you stop fighting the tool and start using it the way it was designed.

Before: you treat Claude Code like ChatGPT-with-tools and wonder why it forgets your project on Monday. After: you see it as a stack-aware, persona-aware agent loop wired into your repo, and you know which file to edit to change its behavior.

Situation: what is Claude Code?

Claude Code is Anthropic’s agentic coding CLI. It runs in the terminal, works with any editor, reads and edits files, runs shell commands, manages git, and integrates with external services through MCP. The reason this course exists is that Claude Code only becomes productive when it is paired with a project template that gives it three things at once:

  1. A persona — who is the AI working as today (engineer, designer, PM, data scientist)?
  2. A stack — what does the codebase look like (Python FastAPI? dbt? Terraform?)?
  3. A phase — where in the work are we (Phase 0 skeleton? Phase 2 implementation?)?

Without those three, every prompt becomes a context re-explanation. With them, you get one of the most expensive pieces of leverage available to a working developer: a senior pair-programmer who already knows your stack.

Task: how this course teaches you to use it

This guide is built around a real template repo (cursor-course-templates) that contains:

  • 4 persona packs in personas/
  • 14 stacks in stacks/ (REST APIs, gRPC, data pipelines, dbt, Terraform, K8s, Ansible, R…)
  • 13 slash commands in .claude/commands/
  • 6 verification agents in .claude/agents/

You will not memorize all of these. You will memorize the 3-step onboarding and the session loop, and look up the rest from this guide as needed.

CMD S --> CMD Ph --> CMD Repo --> AGENT CMD --> AGENT AGENT --> OUT -->
“The AI is not your problem. The context is your problem. Fix the context, the AI fixes itself.”
Debrief — ⏱ 5 min

Ask yourself: in your last AI coding session, how many of the first 10 messages were spent re-explaining your stack? That is the number this course is going to drive to zero.

2. The 3-Step Onboarding

What you get from this section

You will configure a fresh project end-to-end with three commands, and you will see the AI go from “no idea who you are” to “I am ready, guides are active, let’s build” in under five minutes.

Before: you describe your project every single message. After: one command loads all context and the AI knows your stack for the entire session.

The flow

Every project begins with the same three commands, in this order:

/set-persona      # who am I?      (engineer | designer | pm | data-scientist)
/setup-stack      # what am I building?  (skipped for pm/designer)
/start-session    # let's go
B{persona type} B -->|engineer devops data| C[setup stack] B -->|pm designer| D[skip stack] C --> E[start session] D --> E E --> F[ready to build] -->

3. The Four Personas

What you get from this section

You will know exactly what each persona installs into your project, and which one to pick for the job in front of you on Monday.

Before: you have one Claude Code config that drifts toward whoever shouts loudest. After: you switch personas with one command and the AI’s commands, agents, and rules switch with it.

A persona is a directory under personas/{role}/ containing commands, agents, rules, hooks, and an MCP config tailored for that role. Running /set-persona copies the right pack into .claude/ and writes ## Active Persona into CLAUDE.md.

PersonaWhat it activatesStack required?Typical user
engineer Stack picker, /architect, /code-review, /dockerize, code-reviewer + security-auditor agents, TDD rules Yes Backend / API / platform engineers shipping production code
devops IaC stacks, terraform/ansible/k8s skills, infra rules, no app-DB scaffolding Yes SRE, platform engineers, IaC practitioners
data-scientist Notebook stacks, EDA + experiment-tracking commands, reproducibility-checker agent, model-card rules Yes DS, ML engineers, analytics engineers, data engineers
pm PRD scaffolding, story decomposition, INVEST + Given/When/Then rules, gap-detector agent No Product managers collaborating with engineering

How persona-aware commands actually work

Open .claude/commands/architect.md. The first thing it does is persona detection: read ## Active Persona from CLAUDE.md, branch behavior accordingly. The same command does completely different things depending on persona:

CommandEngineerDesignerPMData Scientist
/architect OpenAPI spec / route list Component tree + tokens PRD outline + INVEST stories Experiment plan + metrics
/code-review Security, types, test coverage Token discipline, no logic changes INVEST, GWT, NFR completeness Reproducibility, seed, model card
/next-session Test status, advance phase Responsive check, Figma sync gap-detector run, story counts Experiment log, next hypothesis
Common mistake

Editing the universal command (architect.md) when you really want to change persona-specific behavior. The right place is the persona preamble inside that command, or the persona’s own files in personas/{role}/.

Why this design wins

You can add a new stack in an afternoon by giving it a context.md with the right Architecture Shape and a rules/ directory. Every existing command (/architect, /code-review, /dockerize) will work on the new stack with zero changes — because they branch on the Shape, not on the stack name.

5. Command Reference (with labs)

What you get from this section

For each of the 13 commands in the template: what it does, when to reach for it, the exact invocation, the expected output, and the gotcha that wastes most students 20 minutes.

Before: you guess which command to run and re-read the full .md every time. After: you have a one-screen reference and have actually run each one at least once.

SP[set persona] SP --> SS[setup stack] SS --> AR[architect] AR --> START[start session] START --> WORK[code edit test] WORK --> CR[code review] CR --> NS[next session] NS --> COMMIT[commit] EXIST[Existing repo] --> DET[detect stack] DET --> START -->

/set-persona

What: Activates a persona pack — copies commands, agents, rules, hooks, and MCP config from personas/{role}/ into .claude/ and .cursor/, and writes ## Active Persona into CLAUDE.md. Removes the previous persona’s files first using .persona-manifest.json.

When: First command on a new project. Re-run any time you switch roles.

Invocation:

/set-persona
# interactive menu, pick a number or name
/set-persona engineer    # direct selection

Expected output:

Available personas:
  1. engineer  — build software, ship code
  2. designer  — UI / UX work, design tokens
  3. pm        — product management
  4. data-scientist — notebooks, ML, pipelines

Which persona? > engineer
[OK] Removed previous persona (none).
[OK] Copied personas/engineer/* into .claude/ and .cursor/.
[OK] Wrote ## Active Persona: engineer to CLAUDE.md
[OK] Manifest: .claude/.persona-manifest.json
Gotcha

If client-config/client.md exists, the command will look for a client overlay in client-config/personas/{role}/ and apply it on top of the base. If you didn’t expect that, your output will mention the client name.

/setup-stack

What: Reads the active persona, shows a filtered stack menu, copies stacks/{name}/rules/, context.md, vibe/, templates/ into the project, and writes ## Active Stack + ## Architecture Shape + ## Active Phase.

When: Right after /set-persona, for engineer / devops / data-scientist. PMs and designers skip it.

Invocation:

/setup-stack
# menu is filtered by active persona

Expected output (engineer):

Available stacks for Engineer persona:
  1. python-fastapi   2. go-gin   3. go-grpc
  4. java-spring      5. node-express   6. node-nestjs
> python-fastapi
Stack configured: python-fastapi (REST API). Run /start-session to begin.
Gotcha

If you select a stack that is not in the persona’s allowed list (e.g. devops-terraform when the active persona is engineer), the command rejects it. The validation table in setup-stack.md is the source of truth, not the menu display.

/start-session

What: Loads CLAUDE.md, displays current stack / phase / strictness, asks for a session goal, and confirms readiness.

When: Every time you sit down to work. Cheap to run.

/start-session
> Context Loaded: Python / FastAPI
> Current Phase: Phase 0 (Skeleton)
> Strictness: High
> What is the goal for this session?
< Implement POST /posts with validation and DB persistence.
Gotcha

If CLAUDE.md has no ## Active Persona, the command stops with “Project is not configured. Run /set-persona first.” — this is intentional, not a bug.

/architect

What: Executes Phase 0 — designs the interface contract for your active Architecture Shape and scaffolds a walking skeleton with mocks. Has two modes: Design Mode (AI proposes) and Plan Extraction Mode (use an existing plan.md).

When: Once per feature, before you start writing real code.

Invocation:

/architect "Build a blog API with posts, authors, and tags"
/architect plan.md                # plan extraction mode
/architect requirements.md

What gets scaffolded depends on Architecture Shape:

S{Architecture Shape} S -->|REST API| O1[OpenAPI plus mock routes] S -->|gRPC| O2[proto plus stubs] S -->|Pipeline| O3[stages plus schemas] S -->|Analytics| O4[dbt model tree] S -->|IaC| O5[modules inputs outputs] S -->|GitOps| O6[helm chart skeleton] S -->|Stats| O7[quarto sequence] -->
Gotcha — Plan Extraction Mode

If you pass a plan file, /architect will trust the plan. It will not suggest alternatives or re-design. If the plan says “MongoDB”, you get MongoDB. If you want it to push back, use Design Mode.

Lab 5.1 — Run /architect on a real feature — ⏱ 30 min

Lab 5.1 (engineer track)

Setup: Use the project from Lab 2.1 (engineer + python-fastapi).

Steps:

  1. Run: /architect "Build a tasks API with tasks, projects, and labels. Tasks belong to a project, can have multiple labels, and have a status enum (todo, doing, done)."
  2. Review the proposed entities and endpoints. If anything looks wrong, push back in chat.
  3. Approve the plan. The AI will scaffold mock routes under app/api/ and E2E test stubs under tests/api/.
  4. Install deps and start the server: pip install -r requirements.txt && uvicorn main:app --reload
  5. Open http://localhost:8000/docs — you should see the OpenAPI page with all routes.
  6. Hit GET /tasks and POST /tasks — both should return mock data with HTTP 200/201.

Acceptance criteria:

  • http://localhost:8000/docs shows at least GET /tasks, POST /tasks, GET /tasks/{id}.
  • curl -X POST localhost:8000/tasks -H 'content-type: application/json' -d '{}' returns a mock 201 with a task object.
  • pytest tests/api/ -v runs and all stub tests pass against mocks.
Extension 5.1 — Plan Extraction Mode — ⏱ 20 min

Write a 30-line plan.md for a different feature (e.g. comments). Run /architect plan.md and verify the AI follows your plan exactly. Then introduce a deliberate ambiguity in your plan (e.g. mention “auth” without specifying JWT vs OAuth) and observe the clarification question.

/start-project

What: Models the domain (entities, relationships, interface contract) for a new feature. Persona-aware: produces story maps for PMs, component inventories for designers, data-pipeline designs for DS.

When: When you have a problem statement (“Build a library system”) but not yet a stack-shaped plan. Often used before /architect as a brainstorm step.

/start-project "Library Management System"
Gotcha

/start-project proposes the model; /architect turns it into code. Don’t skip /architect — /start-project will not produce mock endpoints.

/code-review

What: Audits your changes against the active persona’s rules. For engineers: secrets, injection, naming, type safety, test gaps. For DS: reproducibility, seed, model card. Etc.

When: After a meaningful change, before /next-session or commit.

/code-review
> Reviewed 4 files. Found:
>   - WARN tests/api/test_posts.py: assertion-free test on line 42
>   - INFO app/services/post.py: function over 50 lines, consider extracting
>   - PASS no secrets, no SQL injection, type hints present

/next-session

What: Wraps up. Generates a transition document with: session status, where you stopped, next immediate step, files to load. Also advances ## Active Phase if the phase’s acceptance criteria are met.

When: End of every session, before you close the laptop.

/next-session
> # Session Transition
> Last Status: Success (12 tests passing)
> Stopped At: app/services/post.py — extracting validation
> Next Step: implement _validate_author_exists then run pytest
> Context to Load: CLAUDE.md, app/services/post.py, tests/api/test_posts.py

/read

What: Quick context probe — prints active persona, stack, phase, last session summary. Read-only.

When: “Where was I?” questions. The cheapest command in the toolbox.

/dockerize

What: Generates a multi-stage Dockerfile and docker-compose.yml tailored to your stack. Refuses for stacks where Docker is not the artefact (Terraform, Ansible, dbt, R-tidyverse).

When: When you need a container image for deployment or local DB.

Gotcha

Running it on devops-terraform returns a polite refusal — this is intentional. The artefact of Terraform is a .tfplan, not a container.

/detect-stack

What: Brownfield onboarding. Scans package.json, requirements.txt, go.mod, etc., infers the stack and architecture, generates a custom CLAUDE.md.

When: Existing repo, no template config yet.

Gotcha

Set Strictness: Low after running this on legacy code. Otherwise the AI will demand refactors that turn a 1-day feature into a 2-week rewrite.

/research

What: A 3-cycle hypothesis → 5x web search → refutation → refinement loop. Read-only — never edits code. Outputs a Research Artefact.

When: Before implementing anything you’re not 100% sure about. Distributed locking, auth, library choice, etc.

/research "What is the best way to handle distributed locking in Python FastAPI?"

/research-export

What: Generates a polished, shareable research export document (Markdown) summarising findings for a non-AI reviewer (a senior engineer, an architect, a customer).

When: After /research, when you need to convince a human.

/build-diagrams

What: Renders all DIAGRAM_PLACEHOLDER mermaid blocks inside materials/*.html into static .svg files in materials/diagrams/ using mmdc.

When: After editing or adding diagrams in any course material file.

/build-diagrams
# walks materials/*.html, finds <img src="diagrams/...svg">
# next to DIAGRAM_PLACEHOLDER comment, runs mmdc on the mermaid source.

6. The Session Loop

What you get from this section

The full repeating cycle of a working day, from start-session to commit, with one big lab where you take a feature from zero to passing tests in <45 minutes.

Before: you AI-code in unbounded chats that forget themselves at hour 3. After: every session has a goal, a review, and a transition doc — tomorrow-you reads the doc and is back in the saddle in 60 seconds.

B[set goal] B --> C[code and test] C --> D[code review] D --> E{clean} E -->|no| C E -->|yes| F[commit] F --> G[next session] G --> A -->

The cycle, explained

  1. /start-session — AI loads context, asks for goal. You state one concrete deliverable.
  2. Goal & phase check — AI cross-references your goal with ## Active Phase. If you just said “implement payment” while phase is “Skeleton”, AI flags it.
  3. Code — TDD cycle: red → green → refactor. AI uses Edit / Write / Bash tools.
  4. /code-review — AI audits diff against active rules. Fix anything critical.
  5. Commit — /commit built-in or manual git commit.
  6. /next-session — transition doc into plan/sessions/ or stdout for tomorrow.

Demo — ⏱ 15 min

Instructor runs the loop end-to-end on the python-fastapi project: implements POST /tasks with real DB persistence, including a deliberate failing test, a real implementation, and a refactor. Students watch the file system change and the test output transition red → green.

Lab — ⏱ 45 min

Lab 6.1 — One full session, end-to-end

Setup: Continue the project from Lab 5.1 (skeleton already exists with mock POST /tasks).

Steps:

  1. /start-session — goal: “Replace mock POST /tasks with real DB persistence and validation.”
  2. Let the AI write a failing E2E test that posts a real task and reads it back from the DB. Run pytest — confirm it fails (RED).
  3. Let the AI implement the real handler, service, repository. Run pytest — confirm it passes (GREEN).
  4. Ask the AI: “refactor — extract validation into its own private method, no behavior change.” Run pytest — still passes (REFACTOR).
  5. Run /code-review. Fix any flagged issues.
  6. Commit with a meaningful message.
  7. Run /next-session. Save the transition doc to plan/sessions/session-N.md.

Acceptance criteria:

  • pytest tests/api/test_tasks.py -v shows green for both list and create tests, with at least one assertion that reads back from the DB.
  • git log --oneline shows at least one commit you authored in this lab.
  • plan/sessions/session-N.md exists and contains Last Status, Stopped At, Next Step.
  • /code-review output shows zero CRITICAL findings.
Extension 6.1 — Resume tomorrow-you — ⏱ 15 min

Close Claude Code. Open a fresh session. Run /read, then read your transition doc, then /start-session with a goal that picks up where you left off. Time how long it takes you to be productive again. The whole point of the loop is that this number is < 60 seconds.

7. CLAUDE.md Anatomy

What you get from this section

You will know exactly which heading in CLAUDE.md drives which AI behavior, so you can fix issues by editing one file instead of arguing with the model.

Before: the AI ignores your conventions and you don’t know why. After: you grep CLAUDE.md for the offending field, fix it, and the next prompt obeys.

The template-generated CLAUDE.md has five load-bearing sections. Every other thing in the file is decoration.

SectionWhat it controlsRead by
## Active Persona Which preamble runs in every persona-aware command /architect, /start-session, /code-review, /next-session, /read
## Active Stack Which rules are active and which examples to draw from /setup-stack, /architect, /dockerize
## Architecture Shape What kind of skeleton /architect generates /architect, /start-project
## Active Phase What the AI considers in-scope right now (e.g. mock vs real impl) /start-session, /next-session
## Strictness Level How aggressive the AI is about flagging legacy code style violations /code-review, all rule files

Real example after onboarding

# Project Context

## Active Persona
engineer

## Active Stack
python-fastapi

## Architecture Shape
REST API — FastAPI async endpoints, SQLAlchemy 2.0 ORM, Alembic migrations,
Pydantic v2 schemas. Modular monolith pattern.

## Active Phase
Phase 0 (Skeleton)

## Strictness Level
High

## Tech Stack
- Language: Python 3.11+
- Framework: FastAPI
- Database: PostgreSQL (SQLAlchemy 2.0+ AsyncIO)
- Testing: Pytest (AsyncIO)

## Key Rules
- TDD: write E2E tests before implementation
- Layered models: separate DB models from API schemas
- No business logic in routes
- Type hints mandatory
Strictness levels

High: enforce all rules everywhere. New greenfield projects.
Medium: enforce on new code; document but don’t refactor legacy.
Low: brownfield. Match existing patterns. Touch only what is necessary.

Always set Low right after /detect-stack on legacy repos. Otherwise the AI proposes a 4-week refactor for a 2-day feature.

8. Verification Agents

What you get from this section

Six purpose-built agents in .claude/agents/ that catch broken stacks, drifted commands, broken examples, and missing persona branches — the bugs that are invisible until a student runs into them in front of you.

Before: you only find template bugs in workshops, in front of 20 paying students. After: you run the verifier suite before every cohort and find them in 2 minutes.

These agents do not modify code; they audit. Run them with Task tool delegation or directly.

B[stack completeness auditor] A --> C[architect hook verifier] A --> D[example code validator] E[Add or modify a command] --> F[dual tool symmetry checker] E --> G[persona command verifier] H[Add a stack to a persona] --> I[setup stack routing verifier] -->
AgentWhat it checksRun when
stack-completeness-auditor Every stack has context.md with all required headings, ≥ 4 rule files, templates, vibe docs, examples. After adding or editing any stack.
architect-hook-verifier Each context.md gives /architect enough info (entry point, dirs, test cmd, deps) to scaffold without hallucinating. Scores 7/7 = ARCHITECT-READY. Before relying on /architect for a new stack.
dual-tool-symmetry-checker Every file in .claude/commands/ has an identical twin in .cursor/commands/ (and same for agents). Reports drift. After editing any command. CI-friendly.
setup-stack-routing-verifier Every stack listed for a persona in setup-stack.md exists; every stack on disk is routed to exactly one persona. After adding a stack or persona.
example-code-validator Examples in each stack’s examples/ have consistent imports, test fixtures resolve, no deprecated patterns (e.g. dbt tests: vs data_tests:). Before publishing example updates.
persona-command-verifier Every universal command has a persona-detection block; every persona pack has commands/, agents/, persona.md, README.md. After adding or refactoring personas.

Demo — ⏱ 10 min

Instructor deliberately breaks one of the stacks (e.g. removes ## Architecture Shape from stacks/go-gin/context.md), then runs stack-completeness-auditor via the Task tool. The audit finds the regression. Instructor restores the file.

Lab 8.1 — Run the full verification suite — ⏱ 25 min

Lab 8.1

Steps:

  1. Run all six verifiers in parallel using the Task tool: “Run all verification agents in .claude/agents/ in parallel and produce a combined report.”
  2. Read the output. Confirm everything passes on a fresh clone.
  3. Deliberately introduce one regression: pick any stack’s context.md and delete the ## Architecture Shape section.
  4. Re-run stack-completeness-auditor. Confirm it flags the missing section.
  5. Re-run architect-hook-verifier. Confirm the same stack drops to ARCHITECT-FUNCTIONAL or ARCHITECT-BLIND.
  6. Restore the file. Confirm both agents return to PASS.

Acceptance: you can produce, on demand, a single audit report with PASS/FAIL for every stack and every command pair, and you understand which agent to run first when something goes wrong.

10. Hooks & MCP (advanced)

What you get from this section

The two power-user features — hooks for lifecycle automation and MCP for external tool integration — explained at the level you need to extend the template at work.

Before: you copy-paste the same auto-format request every session. After: a 6-line hook formats every edit automatically, and an MCP server lets the AI query your real DB without leaving the chat.

Hooks — lifecycle interceptors

Hooks are shell commands or HTTP calls that fire on Claude Code lifecycle events — PreToolUse, PostToolUse, SessionStart, UserPromptSubmit, etc. Configure them in .claude/settings.json.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{
          "type": "command",
          "command": "jq -r '.tool_input.file_path' | xargs ruff format"
        }]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "if echo \"$TOOL_INPUT\" | grep -qE '(rm -rf /|drop database)'; then echo BLOCKED >&2; exit 2; fi"
        }]
      }
    ]
  }
}

Exit code 2 blocks the action; any other non-zero is fail-open.

MCP — Model Context Protocol

MCP servers expose tools to Claude Code over stdio, HTTP, SSE, or WebSocket. Configure in .mcp.json:

{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "uvx",
      "args": ["mcp-server-github"]
    },
    "postgres": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://user:pass@localhost/db"]
    },
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"]
    }
  }
}

Restrict which MCP tools are auto-allowed in .claude/settings.json:

{
  "permissions": {
    "allow": ["mcp__github__*"],
    "deny": ["mcp__github__delete_*"]
  }
}
Extension 10.1 — Add a real MCP server — ⏱ 20 min

Install the playwright MCP server, add it to .mcp.json, restart Claude Code, and ask: “Open my running FastAPI server at localhost:8000/docs and screenshot the tasks endpoint.” No hand-holding — if you hit a permission prompt, decide whether to add it to your allow list and why.

11. How to Adapt This After Class

What you get from this section

A concrete plan to take this template into your real job on Monday — per role — plus the three pitfalls that kill most adoptions.

Before: the workshop ends, you keep using ChatGPT-style chats. After: you have a checklist for your specific repo.

By role

If you are a software engineer

  1. Run /detect-stack on your real repo. Read the generated CLAUDE.md with a critical eye.
  2. Set Strictness: Low for legacy code, High for greenfield modules.
  3. Add team conventions (commit format, branch naming, CI gate names) to CLAUDE.md under ## Team Conventions.
  4. Commit .claude/ and CLAUDE.md to the repo. Now your AI behavior is shared with the team like any other config.
  5. Add a hook that runs your linter on PostToolUse. Stop fixing trailing whitespace by hand.

If you are a data scientist

  1. Pick the right stack: python-datascience for notebooks, python-spark for distributed pipelines, python-dbt-snowflake for SQL transforms, python-mlops for model serving.
  2. Update ## Key Rules with your team’s seed convention, MLflow URI, and data path layout.
  3. Add a custom rule under .claude/rules/data-paths.md with the absolute paths you use (S3 prefix, GCS bucket, etc.).
  4. Wire MCP to your warehouse (Snowflake, BigQuery) read-only. Then ask the AI to write dbt tests against real schemas.

If you are in DevOps / platform

  1. Pick devops-terraform, devops-ansible, or devops-k8s-helm based on your primary artefact.
  2. Update ## Environment Strategy in CLAUDE.md with your real env layout (dev/staging/prod, Terragrunt vs workspaces, etc.).
  3. Pin provider and module versions explicitly. The AI will respect them; without them, it guesses latest.
  4. Add a hook that runs terraform validate + tflint on PostToolUse for any .tf file.

If you are a PM

  1. Run /set-persona pm — no stack. /start-session directly.
  2. Drop your existing PRD into the repo. Run /code-review — the gap-detector will flag stories without acceptance criteria.
  3. Use /architect on a new feature description. The AI will translate it into INVEST stories with Given/When/Then ACs — that you then hand to engineering.

Common pitfalls in real environments

PitfallSymptomFix
Corporate proxy / TLS interception Web search, MCP HTTP, or WebFetch tools fail with cert errors Set NODE_EXTRA_CA_CERTS and SSL_CERT_FILE to your corporate cert. For npm-based MCP servers, run npm config set cafile.
SSO / Okta auth on internal tools MCP servers for internal GitHub Enterprise / Jira don’t connect Use a personal access token with the minimum scopes; store in .claude/settings.local.json (gitignored).
Team CLAUDE.md conventions drift Different team members get different AI behavior on the same repo Commit CLAUDE.md + .claude/. Run dual-tool-symmetry-checker in CI. Treat the file like any other config — PR reviews, no surprise edits.
Strictness too high on legacy code AI proposes massive refactors for trivial features Set Strictness: Low globally, Medium in new modules via a folder-scoped CLAUDE.md.
Persona-aware command edited at the universal level Behavior change leaks to other personas Edit only inside the persona preamble block, or in personas/{role}/. Run persona-command-verifier to confirm.

Three next steps, ordered by impact

  1. Today: commit .claude/ and CLAUDE.md to your real repo. Even with default settings, this beats unbounded chat.
  2. This week: add one custom rule file under .claude/rules/ capturing the single most common feedback you give in code review. The AI will start enforcing it for free.
  3. This month: add one MCP server that gives the AI read-only access to a system you currently context-switch to (your warehouse, your monitoring, your issue tracker). Measure the saved minutes.
“The AI’s ceiling is the quality of the context you give it. Everything in this template — persona, stack, rules, hooks, MCP — is just a way to raise that ceiling without typing the same paragraph twice.”
