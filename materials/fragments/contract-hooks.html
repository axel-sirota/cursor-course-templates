7. Contract Gates: Hooks That Push Back

Everything so far trusts the agent to notice its own mistakes. That trust runs out the moment two agents build against the same contract: the payments agent can emit an event the notifications agent never expected, and both will happily report success. A contract gate fixes this by validating the agent’s work at the moment it tries to finish — and refusing to let it stop until the contract holds.

SubagentStop: the exit that can say no

The gate is built on one hook event: SubagentStop. It fires when a subagent believes it is done, and unlike most hooks it can overrule that belief.

  • When it fires: the moment a subagent finishes its turn and tries to return control.
  • What it receives: input JSON on stdin carrying agent_type and last_assistant_message — enough to know who is stopping and what they claimed.
  • Exit code 0: the stop goes through; the subagent is done.
  • Exit code 2: the stop is blocked. Whatever the hook wrote to stderr is fed back to the agent as feedback, and the agent keeps working on it.
  • The cap: a stop can be blocked at most 8 times. After that the agent stops regardless, so a broken validator cannot trap an agent forever.

That exit-code-2 path is the whole trick. The validator does not warn, log, or hope — it bounces the agent back into its own session with the failure text in hand.

Why the gate lives in the agent’s frontmatter

You could wire a Stop hook at the session level, but there is a placement detail that matters: a hook declared in an agent’s frontmatter runs with that agent’s worktree as its working directory, and is auto-converted to SubagentStop when the agent runs as a subagent. That means validate.sh checks the agent’s actual work — the fixtures it just edited in its own worktree. A session-level hook runs from the main checkout and cannot easily find which worktree the finishing subagent was working in.

This is the canonical block, exactly as the payments agent ships it:

Stop:
  - hooks:
      - type: command
        command: "bash \"$CLAUDE_PROJECT_DIR\"/contracts/validate.sh services/payments"

Each service agent carries the same block pointing at its own service directory. The script is the shared validator from section 2’s monorepo: it loads every fixture under services/<name>/fixtures/ and checks it against the schemas in contracts/.

You Wire Hooks, You Don’t Write Them

The hooks in this course are shipped, not hand-written in class. The sample monorepo provides path_guard.py, agent_activity.py, and validate.sh ready to use — the class is about wiring them into agents and observing what they do, not about hook authoring.

Demo 6 — the gate fires for real

The python monorepo ships with an intentional contract violation: a notifications fixture uses event_type "refund.done", which is not in the NotificationEvent enum (refund.approved, refund.rejected). Nobody planted a bug in code — the data itself is out of contract, which is exactly the kind of drift a reviewer skims past and a gate does not.

Point the notifications agent at its own fixtures:

cd sample-monorepo/python-fastapi
claude
> Use the notifications agent to verify your fixtures against the contract.

The agent inspects the fixtures, concludes they look reasonable, and tries to stop. Its Stop hook runs validate.sh services/notifications, the validator hits the bad enum value, and the stop is blocked: 

FAIL fixtures/notification_refund_done.json: field "event_type" value "refund.done" not in enum [refund.approved, refund.rejected].

That FAIL line is delivered straight back into the agent’s session as feedback. The agent is not done anymore — it reads the message, opens the fixture, and makes the smallest fix that satisfies the contract: 

-  "event_type": "refund.done",
+  "event_type": "refund.approved",

On its second attempt to stop, the hook runs again — and this time the gate opens: 

PASS fixtures/notification_refund_done.json

Two stop attempts, one blocked, zero human intervention. The agent was forced to fix its own work because the gate would not let it leave otherwise.

Lab 6 — break it yourself

Easy

Break a payments fixture so it violates contracts/refund.schema.json, then run the payments agent and ask it to verify its fixtures. Watch the gate block the stop and force the fix — without you saying what is wrong.

Hard

Add a required "reason" field to NotificationEvent in contracts/notification.schema.json, and extend contracts/validate.py so the gate enforces the tightened contract end to end. The existing notifications fixtures should now fail the gate until they carry a reason.

You succeeded when:

  • the transcript shows a blocked stop,
  • the hook’s FAIL feedback appears in the agent’s session,
  • and a re-validation passes on the next stop attempt.
