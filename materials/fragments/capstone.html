Everything so far ran against the sample repo. This section runs the whole stack against your monorepo — about 35 minutes, you drive, the instructor circulates. Treat it as a runbook: six steps, each with a verification gate. Do not move to the next step until the gate passes; a skipped gate here is a debugging session later.

The six-step checklist

  1. Detect your stack. Run /detect-stack at the root of your monorepo and read the report critically — it decides which adaptation row below applies.
    Gate: the detected stack, test runner, and service layout match what you know to be true. If it misreads your repo, correct the generated context before continuing.
  2. Write nested CLAUDE.md files. Cover at least two of your services: root file holds shared conventions, each service file holds only what is unique to that service — zero duplication between levels.
    Gate: /context lists the root file plus the service file under Memory files when you work inside that service, and no rule appears twice.
  3. Create two service-scoped agents. Each gets the isolation treatment: its own worktree, a restricted tool list, and the path_guard hook copy-adapted from the sample monorepo so its paths name your services.
    Gate: ask agent A to edit a file owned by agent B’s service and watch the hook block it.
  4. Configure worktree settings. In .claude/settings.json set "baseRef": "head" and symlinkDirectories for your dependency directory (see the table). If your repo is large, add sparsePaths so each agent checks out only its slice.
    Gate: a fresh worktree runs your test suite green without reinstalling dependencies.
  5. Run a real parallel implementation. Pick a real ticket that touches two services, adapt /implement-across-services to your service names, and launch it. Resist the urge to micromanage — watch the activity log instead.
    Gate: both agents finish on their own branches and each branch passes its service’s tests.
  6. Merge and measure. Merge the branches in dependency order — provider service first, consumer second — and rerun the full test suite on the result. Then compare /context inside a service against your pre-capstone baseline.
    Gate: a clean merge, a green suite, and a concrete token number for what the nested layout saved you.

Adapting to your stack

The course ships worked templates for the python-fastapi and node-express variants. The java-spring and go-gin rows are honest about that: you adapt the shipped templates rather than copy a ready-made one.

Stack Test command symlinkDirectories target Service context files
python-fastapi .venv/bin/python3 -m pytest .venv services/<name>/CLAUDE.md (shipped template)
node-express npm test --workspace=<service> node_modules services/<name>/CLAUDE.md (shipped template)
java-spring ./mvnw test -pl <module> ~/.m2 is already shared per user; do not symlink target/ — each worktree builds its own <module>/CLAUDE.md, adapted from the python template
go-gin go test ./services/<name>/... usually none — the Go build cache lives in ~/.cache/go-build, outside the worktree services/<name>/CLAUDE.md, adapted from the node template
Take It Home

Finish the rollout. Add agents for your remaining services — the second one takes a fraction of the time the first did.

Commit the .claude/ config. Hooks, settings, and agents in version control mean your whole team inherits the setup instead of rebuilding it.

Make /catchup a habit. After every /clear, it is the cheapest way back to full working context.

Lab 9 — the real thing

Easy

Run the six-step checklist against the sample monorepo variant matching your stack. Every gate must pass before you tick the step.

Hard

Run the checklist against your actual repo with a real ticket from your backlog as the step-5 parallel implementation.

You succeeded when: two agents implemented in parallel on separate branches and both merged cleanly.
