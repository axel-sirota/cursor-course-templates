6. Parallel Implementation Across Services

Everything so far — subagents, worktrees, per-service CLAUDE.md files, token budgets — has been building toward this section. The sample monorepo ships a custom command, /implement-across-services, that takes one feature spec and implements it across all three services at the same time: one subagent per service, each in its own worktree, coordinated by the lead session you are typing into.

The refunds feature in specs/feature-refunds.md is the perfect test case. It touches every service — gateway accepts POST /refunds, payments makes the approve/reject decision, notifications records the outcome — but the services only meet at the JSON Schemas in contracts/. Three agents can build three services independently precisely because the contract, not conversation, defines where they touch.

Anatomy of the Command

/implement-across-services <spec-file> runs in four phases. The command file spells each one out so the lead session cannot improvise its way into a mess:

  1. Read the spec. The lead session reads the feature spec in full and extracts each service’s responsibilities and acceptance criteria. It does not start implementing anything itself.
  2. Spawn all three service agents in one message. The lead issues three Agent tool calls — payments, notifications, gateway — in a single response block. Each agent gets its own worktree, its own service directory, and only the slice of the spec it owns.
  3. Collect completion reports. Each agent finishes by returning a small JSON report: which branch it worked on, which files it touched, and whether its service’s tests pass. The lead does not proceed until all three reports are in.
  4. Merge sequentially, in dependency order. The lead — and only the lead — merges the three worktree branches back one at a time: payments, then notifications, then gateway, running contracts/validate.sh after each merge so a contract break is caught at the merge that introduced it.

Two lines in the command file carry most of the weight. The first forces the fan-out to actually be parallel: 

CRITICAL: run these in PARALLEL using multiple Agent tool calls in a single message, not sequentially

Without that line, the model will happily launch agent one, wait for it to finish, launch agent two, and so on — technically using subagents, practically sequential. Parallel tool calls in a single message are what make three agents run at once. The second line governs the way back: 

MERGE PHASE (you are the sole merger): merge each agent's worktree branch back sequentially in dependency order — payments, then notifications, then gateway — running contracts/validate.sh <service-dir> after EACH merge
One Merger, Always

The fan-out is parallel; the merge never is. Agents never merge their own branches — they report and stop. If three agents raced to merge into main, you would trade file conflicts (which worktrees solved) for merge conflicts (which nothing solves for free). One merger, a fixed dependency order, and a contract check between merges turns integration from a race into a pipeline.

Wall-Clock vs. Tokens

Be clear about what parallelism buys you. Three agents working at once finish in roughly the time of the slowest one, so a feature that would take three sequential agent runs lands in about a third of the wall-clock time. What it does not buy you is tokens: three agents means three separate contexts, each loading its own instructions, its own service files, and its own conversation — and each billed separately. If anything, parallel runs cost slightly more tokens than one careful sequential session, because shared context (the spec, the contracts) is loaded three times instead of once.

You are spending tokens to buy wall-clock time. On a three-service feature with an afternoon deadline, that is an excellent trade. It is not always the right one.

When Sequential Is Still Right

Tiny changes. If the whole feature is a two-line edit per service, the worktree setup and triple context load cost more than they save. One session editing three files wins.

Heavy cross-service coupling. If the services need to negotiate as they go — the payload shape is still being discovered, or a contract change is part of the work — parallel agents will each guess differently and you will pay for it at merge time. Settle the contract first, or work sequentially in one context that sees all three services.

Demo 5 — The Parallel Run

Full walkthrough — run this in your copy of the Python monorepo. You need two terminals: one for the lead session, one to watch the agents work.

Terminal 1 — start the lead session and kick off the run:

cd ~/labs/refund-monorepo
claude
/implement-across-services specs/feature-refunds.md

The lead reads the spec, then fires all three Agent calls in one message. From this point on, terminal 1 is mostly quiet until the reports come back.

Terminal 2 — watch the three agents interleave. Every tool call any agent makes passes through the agent_activity PostToolUse hook, which appends one JSON line to logs/tool_usage.jsonl: 

tail -f logs/tool_usage.jsonl

This is the moment the section is named after: three streams of Read/Write/Bash events, tagged with different worktree paths, interleaved in real time. No agent ever touches a file outside its own service directory — the worktree isolation from section 3 is doing its job while you watch.

When all three reports are in, the lead merges the branches back — payments, then notifications, then gateway — running contracts/validate.sh after each one. Afterwards, look at the shape of the history: 

git log --oneline --graph

Three short-lived branches, one per service, each merged into main by a single merger in a fixed order. That graph is the signature of a healthy parallel run — keep a mental picture of it, because in Lab 5 you produce it yourself.

Lab 5 — Run It and Race It

Easy

Before you start, write down your estimate: how long would implementing the refunds spec take as three sequential agent runs? Then run /implement-across-services specs/feature-refunds.md and time it. When it finishes, verify that each agent’s changes landed on a separate branch and that each branch touches only its own service’s directory. Compare wall-clock reality against your sequential estimate.

Hard

Edit the spec so that two services need the same contract change — for example, a new field that payments must emit and notifications must record. Re-run the command and deal with what happens at merge time: the contract change has to land in the right order for contracts/validate.sh to pass after every merge, not just the last one. Resolve it without ever letting an agent merge its own branch.

You Succeeded When…

You succeeded when: git log --oneline --graph shows three merged branches and validate.sh passes for all services.
