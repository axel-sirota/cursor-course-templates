3. Worktree Isolation

Subagents that share your checkout also share your uncommitted state. Two agents editing the same tree can trample each other’s files, and a half-finished agent run leaves debris in git status that you have to untangle by hand. Worktree isolation removes the problem at the git layer: each agent gets its own checkout, its own branch, and its own blast radius.

What isolation: worktree Actually Does

Setting isolation: worktree in an agent definition changes where that agent runs. Instead of operating on your checkout, each run gets a temporary git worktree:

  • The worktree is created under .claude/worktrees/<name>, on a dedicated branch named worktree-<name>.
  • Every file the agent reads, writes, or executes lives inside that directory. Since v2.1.203, the agent’s Bash tool is confined to the worktree as well — a stray rm or test command cannot touch your main checkout.
  • The docs describe auto-cleanup: a run that ends with no changes should have its worktree and branch removed automatically. On CLI 2.1.218 we observed the worktree persisting after a no-change run — holding only the .venv symlink — so budget for manual cleanup with git worktree remove. Demo 2 shows it live.
  • If the agent did commit work, the worktree stays behind so you can inspect, cherry-pick, or merge the worktree-<name> branch on your own terms.
Housekeeping: gitignore the worktree root

Add .claude/worktrees/ to your .gitignore. Worktrees are nested inside the repo directory, and without the ignore entry every agent run pollutes git status in your main checkout — the exact noise isolation is supposed to remove. The sample monorepo ships this entry already.

The #1 Gotcha: Worktrees Branch from the DEFAULT Branch

By default, a new agent worktree branches from the repository’s default branch (usually main) — not from your current HEAD.[2] If your feature spec, contracts, or scaffolding live on a feature branch, every worktree-isolated agent silently implements against code that does not contain them. The agents look busy, the diffs look plausible, and the result is wrong.

The fix is one setting in .claude/settings.json, which the sample monorepo ships: 

{
  "worktree": {
    "baseRef": "head"
  }
}

With "baseRef": "head", worktrees branch from whatever commit you have checked out — agents see the same code you see. Leave the default ("fresh") only when you deliberately want agents to start from a clean default-branch state.

The Fresh-Checkout Survival Kit

A worktree is a fresh checkout: it contains only tracked files. Two categories of things your project depends on are therefore missing, and without them every agent’s first test run fails before it does any useful work:

  1. Gitignored files the code needs — .env is the classic case. A .worktreeinclude file at the repo root lists gitignored paths that should be copied into each new worktree: 
    # .worktreeinclude — gitignored files every agent worktree still needs
.env
  2. Heavy dependency directories — .venv, node_modules. Copying gigabytes per agent is a non-starter; worktree.symlinkDirectories symlinks them from the main checkout instead, so every worktree shares one installed set: 
    {
  "worktree": {
    "baseRef": "head",
    "symlinkDirectories": [".venv"]
  }
}

    For the Node variant of the sample monorepo the list is ["node_modules"] instead. Symlinked directories are shared state — fine for read-mostly dependency trees, wrong for anything agents should mutate independently.

With baseRef, .worktreeinclude, and symlinkDirectories in place, the picture looks like this: three agents branch from the same base in parallel, work in complete isolation, and their branches merge back one at a time.

Demo 2 — Watch the Isolation

This demo makes the invisible machinery visible: you spawn a worktree-isolated agent, then watch git from a second terminal while it works.

  1. Give an agent worktree isolation

    In the sample monorepo, add isolation: worktree to a small agent’s frontmatter — for example a docs agent that only touches one file: 

    ---
name: changelog-scribe
description: Adds a dated entry to CHANGELOG.md summarizing recent changes.
tools: Read, Edit, Bash
isolation: worktree
---
Read the git log since the last CHANGELOG entry and append a new dated
entry to CHANGELOG.md. Keep entries to one line each.

  2. Spawn it on a small task

    In Claude Code:

    > Use the changelog-scribe agent to add a changelog entry
  for the refunds feature.

  3. In a second terminal: catch the worktree in the act

    While the agent runs, list worktrees and branches from the repo root:

    git worktree list
git branch --list 'worktree-*'
    $ git worktree list
/private/tmp/refund-monorepo                                           cc106e8 [main]
/private/tmp/refund-monorepo/.claude/worktrees/agent-a3643a1fcff8ba6e5 cc106e8 [worktree-agent-a3643a1fcff8ba6e5] locked

$ git branch --list 'worktree-*'
+ worktree-agent-a3643a1fcff8ba6e5

    Both checkouts point at the same commit, cc106e8 — a commit made minutes earlier on main. The agent branched from your HEAD because baseRef is "head"; a default-branch worktree would sit on the older initial commit.

  4. Confirm your checkout stays clean

    Still in the second terminal:

    git status
    On branch main
nothing to commit, working tree clean

    The agent is editing files right now, and your working tree shows nothing. All of its changes live in the .claude/worktrees/agent-… directory you just saw in git worktree list.

  5. See what a no-change run leaves behind

    Run the agent again with a task that produces no edits (“check whether the changelog already covers the refunds feature — change nothing”). The docs describe auto-cleanup for this case; on CLI 2.1.218 we observed the worktree persisting instead, holding only the .venv symlink that symlinkDirectories put there: 

    $ git worktree list
/private/tmp/refund-monorepo                                           1632699 [main]
/private/tmp/refund-monorepo/.claude/worktrees/agent-ae1ac0745d7fc74a8 1632699 [worktree-agent-ae1ac0745d7fc74a8]

$ git status --short   # run inside the leftover worktree
?? .venv               # only the .venv symlink from worktree.symlinkDirectories

    So treat cleanup as manual until your CLI version proves otherwise: 

    git worktree remove --force .claude/worktrees/agent-ae1ac0745d7fc74a8
git branch -D worktree-agent-ae1ac0745d7fc74a8

Lab 2 — Base Branch Forensics

Easy

Take the agent you built in Lab 1 and give it isolation: worktree. Run it on a small task, then — while it runs or right after — locate its worktree directory and its worktree-* branch using git commands, and verify that your main checkout’s git status stayed clean the whole time.

Hard

Create a feature branch with at least one commit that main does not have. Run your worktree-isolated agent twice from that branch: once with worktree.baseRef set to "fresh" and once with "head". Using git log on each run’s worktree-* branch, prove which commit each worktree branched from — and predict, before looking, which run can see your feature-branch commit.

You succeeded when: you can explain which base commit the agent saw and why.
