4. Nested CLAUDE.md: Hierarchical Context

A monorepo has one repo but many contexts. The payments service cares about idempotency keys and migration order; the gateway cares about routing tables and rate limits. Stuffing all of it into one root CLAUDE.md means every session pays for every team’s notes. Claude Code solves this with hierarchical context: a CLAUDE.md per directory level, each loaded only when it is relevant.

The loading rules

Three rules govern which files reach the context window:

Where the CLAUDE.md livesWhen it loads
Repo root, or any ancestor of your working directory In full, at session launch
A subdirectory below you (e.g. services/payments/) Lazily — the first time Claude reads a file in that subtree
A sibling directory you never touch Never

The third rule is the one that makes monorepos workable: a session focused on the gateway never sees the payments migration notes, no matter how long it runs. Context isolation between services is free — you get it just by putting the notes where the code is.

Size discipline

Lazy loading only pays off if each level stays small. The working budget: root CLAUDE.md under 200 lines, each service file under 150 lines, and zero duplication between levels. If a rule applies to every service, it belongs at the root; if it applies to one service, it belongs in that service’s file — never both. Duplicated rules drift, and the copy Claude reads last wins in ways you can’t predict.

For packages owned by other teams that you never want in your sessions at all, add their paths to claudeMdExcludes in your settings — their CLAUDE.md files then stay out of context even if Claude reads a file there.

What /compact forgets

Compaction does not treat all context sources equally. After a /compact:

Context sourceAfter /compact
Project-root CLAUDE.mdRe-injected from disk — survives
Nested CLAUDE.md filesLost until a matching file is read again
Path-scoped rulesLost until a matching file is read again

So a long payments session that compacts mid-task silently drops the payments conventions it started with. This is the principled reason the next section prefers /clear + /catchup over /compact in monorepos: a fresh session replays the loading rules deterministically instead of hoping the summary kept the right notes.

Demo 3 — watch the lazy load happen

The loading rules are easy to state and easy to disbelieve. The InstructionsLoaded hook fires every time a context file enters the session, so a two-line hook turns the rules into a visible log.

  1. In your copy of the sample monorepo, register the hook in .claude/settings.local.json (local settings, so the shared settings.json stays untouched): 

    {
  "hooks": {
    "InstructionsLoaded": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "command": "cat >> \"$CLAUDE_PROJECT_DIR\"/instructions-loaded.log"
          }
        ]
      }
    ]
  }
}

  2. Open a second terminal and watch the log:

    cd sample-monorepo/python-fastapi
touch instructions-loaded.log
tail -f instructions-loaded.log

  3. Launch claude at the monorepo root. The root CLAUDE.md event appears in the log immediately — that is rule one. Now touch the payments service: 

    claude
> Read services/payments/README.md and summarize the service in two sentences.

    The moment Claude reads a payments file, a second event lands in the log: services/payments/CLAUDE.md has lazy-loaded. That is rule two.

  4. Keep working inside payments for a few more turns, then check for the sibling: 

    grep payments instructions-loaded.log
grep gateway instructions-loaded.log || echo "gateway CLAUDE.md never loaded"

    Expected result — payments present, gateway absent, rule three on the record:

    $ grep payments instructions-loaded.log
{"hook_event_name":"InstructionsLoaded","path":"services/payments/CLAUDE.md", ...}
$ grep gateway instructions-loaded.log || echo "gateway CLAUDE.md never loaded"
gateway CLAUDE.md never loaded

Lab 3 — author a service context

Easy

The sample monorepo’s services/notifications/CLAUDE.md is yours: rewrite it for your own style and stack conventions. Constraints: under 150 lines, and nothing duplicated from the root CLAUDE.md. Then prove lazy loading — run /context and note the “Memory files” list before touching notifications, have Claude read one notifications file, and run /context again.

Hard

First prove sibling isolation: work an entire session inside one service and show the other services’ CLAUDE.md files never appear in /context. Then add claudeMdExcludes to your settings to suppress one service’s file entirely, read a file in that service, and verify with /context that the exclusion held.

You succeeded when: /context’s Memory files list shows exactly the files you predicted, in both states — before and after the read.
