2. Service-Scoped Subagents

A subagent is a separate Claude instance that the lead session spawns to do one job with its own fresh context window. In a monorepo, the natural unit of delegation is the service: one agent that knows the payments service, one for the gateway, one for notifications. Each agent is a Markdown file in .claude/agents/ — the frontmatter configures it, and the body of the file is the agent’s system prompt. The lead session reads the description field to decide when to delegate, hands the agent a task, and gets back a report instead of a wall of intermediate tool calls.

The agent file: frontmatter reference

Everything about an agent is declared in the YAML frontmatter of its .claude/agents/<name>.md file. These are the fields you will use in this course:

FieldMeaning
nameUnique identifier; how the lead session (and you, in prompts) refer to the agent.
descriptionWhen to use this agent — the lead reads this to decide whether to delegate a task here.
toolsStrict allowlist of tool names the agent may call. A tool not on the list simply does not exist for this agent.
disallowedToolsExplicit denylist subtracted from the allowlist; useful to inherit defaults but carve out exceptions.
modelWhich model runs the agent (sonnet, opus, haiku, or inherit to match the lead).
effortReasoning-effort level for the agent’s model — dial down for mechanical tasks, up for design work.
maxTurnsHard cap on the agent’s turns before it is stopped — a runaway-loop budget.
colorAccent color for the agent’s entries in the transcript, so parallel agents are tellable apart.
isolationExecution isolation for the agent (e.g. running in its own worktree) so its edits stay off your checkout.
hooksPer-agent lifecycle hooks (e.g. PreToolUse) that fire only for this agent’s tool calls.
memoryPersistent memory directory for the agent, carried across sessions instead of starting blank each time.

Below the frontmatter comes plain Markdown: the agent’s system prompt. That is where you state its scope (“you own services/payments and nothing else”), its working rules, and its reporting format.

The completion-report contract

A subagent’s final message is the only thing the lead session keeps, so make it machine-checkable. The pattern used throughout this course: the agent’s system prompt ends with an instruction to close every task with a fenced JSON block in a fixed shape. 

{
  "agent": "payments-implementer",
  "task": "add an amount-format check to payments",
  "status": "green",
  "files_changed": ["services/payments/src/refunds.py"],
  "tests_run": ".venv/bin/python3 -m pytest services/payments — 12 passed",
  "notes": ""
}

The lead (or a script in CI) can parse this block instead of re-reading the agent’s whole transcript: status (green or red) gates the merge, files_changed is checked against the agent’s declared scope, and notes carries anything the orchestrator needs for the merge — including any blocked attempts worth looking at.

Write-scoping is a hook, not a permission

Subagents inherit the session’s permissions and have no per-agent cwd. The tools allowlist is all-or-nothing per tool, never per path: you can take Edit away from an agent entirely, but you cannot tell Edit “only inside services/payments” with the allowlist alone. The mechanism that stops the payments agent from editing gateway files is a per-agent PreToolUse hook that inspects the target path and exits 2 to block the call: 

hooks:
  PreToolUse:
    - matcher: "Edit|Write"
      hooks:
        - type: command
          command: "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/path_guard.py services/payments"

This block is the canonical wiring used by every scoped agent in the sample monorepo — copy it verbatim and change only the service path argument.

New agents/ directory? Restart the session

Agent files are discovered at session start. The first file you add to a brand-new .claude/agents/ directory will not load into the running session — restart claude and it appears. Subsequent edits to existing agents are picked up normally.

Demo 1 — a scoped agent in action

Open your copy of the sample monorepo (python variant) and look at the payments agent that ships with it, then delegate a small change and watch where the edits land. 

cd ~/labs/refund-monorepo        # your copy of sample-monorepo/python-fastapi
cat .claude/agents/payments-implementer.md
claude

The cat shows the pattern from this section in one file: a tools allowlist, the canonical path_guard hook pointed at services/payments, and a body that pins the agent’s scope and demands the JSON completion report. Inside the session, delegate: 

> Use the payments-implementer agent to add an amount-format check to payments

In the transcript, every read may roam (the agent is allowed to look at contracts and neighbors), but every Edit and Write stays inside services/payments/: 

⏺ Task(payments-implementer): add an amount-format check to payments
  ⎿ Read(services/payments/README.md)
  ⎿ Read(contracts/payment.schema.json)
  ⎿ Edit(services/payments/src/refunds.py)
  ⎿ Bash(.venv/bin/python3 -m pytest services/payments -q)
      12 passed
  ⎿ Agent reply (final message):
      {
        "agent": "payments-implementer",
        "task": "add an amount-format check to payments",
        "status": "green",
        "files_changed": ["services/payments/src/refunds.py"],
        "tests_run": ".venv/bin/python3 -m pytest services/payments — 12 passed",
        "notes": ""
      }

Two things to point at in the real run: the only files under Edit/Write are payments files, and the final message is exactly the machine-checkable report the agent’s system prompt demanded.

Lab 1 — rebuild the notifications agent

The monorepo ships a notifications agent too — but you will rebuild it from scratch to feel the difference between tool-level and path-level scoping. Move the shipped one aside first (mv .claude/agents/notifications-implementer.md .claude/agents/notifications-implementer.md.bak), then rebuild it from the payments agent as a template, twice — once per tier below. When you finish, compare your version with the shipped one and restore it — Demo 5 needs the shipped agent back in place.

Easy

Create notifications-implementer from the payments agent as a template, with Write and Edit removed from its tools list. Delegate a change to the notifications service and prove the allowlist blocks all writes — including ones inside services/notifications. That is the point: allowlists gate tools, not paths.

Hard

Restore Write and Edit, then wire path_guard.py into the agent’s frontmatter hooks scoped to services/notifications. Prove both directions: an attempted gateway edit dies with exit 2, while a notifications edit goes through. Path-scoping is the hook’s job.

You succeeded when: the blocked attempt appears in the transcript with the hook’s BLOCKED message.
