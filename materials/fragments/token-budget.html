5. Reading Your Token Budget

The previous section made a claim you should not take on faith: nested CLAUDE.md files load lazily, so a scoped layout keeps most of its instructions out of the window until a file in that service is actually touched. Claude Code ships the instrument to check that claim: /context. This section teaches you to read it, and to re-measure after every change you make to your memory layout.

What /context Shows

Run /context inside any session and you get a breakdown of the context window, category by category:

CategoryWhat it contains
System promptClaude Code's own operating instructions — fixed per version, not yours to tune
System toolsDefinitions of the built-in tools (Read, Edit, Bash, …)
MCP toolsTool schemas from every connected MCP server — grows with each server you add
Memory filesEvery CLAUDE.md and rule file currently loaded — listed by path
MessagesThe conversation so far: your prompts, Claude's replies, tool results
Free spaceWhat remains before the window fills and compaction kicks in

The row that matters for this module is Memory files. It is not just a number — it lists each loaded file by path. That list is the verification surface for the launch-time half of the previous section’s rules: after /clear on a scoped layout you should see the root CLAUDE.md only; on the flat layout, the one fat file. One caveat, measured in Demo 4: on CLI 2.1.218 the table shows the files loaded at session launch — a mid-session lazy load is proven by the InstructionsLoaded hook log from Demo 3, not by a new row here.

Do not confuse the two budget commands. /context shows what is occupying the current session's context window right now. /usage shows how much of your plan's rate limits (session and weekly) you have consumed — a billing view, not a window view.

The /clear + /catchup Pattern

When a long session bloats the Messages category, the reflex is /compact. In a nested-memory monorepo that reflex has a hidden cost: compaction summarizes the conversation, and lazily loaded CLAUDE.md files ride along in that summarization — the payments rules you triggered two hours ago may survive only as a vague paraphrase, or not at all. The window looks healthy; the instructions are gone.

The pattern that preserves correctness is /clear followed by /catchup. /clear drops the window to its baseline. /catchup (a custom command this course ships in .claude/commands/catchup.md) rebuilds exactly the working state you need by re-reading what changed — and because reading a service's files re-triggers that service's lazy CLAUDE.md load, the right nested rules come back as real files, not as summary residue. The command runs five steps:

  1. git diff main...HEAD --name-only to list the files changed on this branch (falling back to git status --short when already on main or the diff is empty).
  2. Read each changed file in full.
  3. Read the CLAUDE.md of any service whose files appear in that list — re-triggering the lazy load of exactly the rules the work needs.
  4. Summarize the state of the work in at most 10 bullets: what changed relative to main, and what is in flight.
  5. Declare which memory files are now loaded — which you verify with /context.
Measure the delta, not the total

Absolute /context numbers are not comparable across machines: your MCP servers, plugins, and Claude Code version all shift the totals. The honest measurement is the Memory files category compared between two runs on the same machine — flat layout vs. scoped layout, before compaction vs. after recovery.

The captured runs below measured a 68.6% Memory-files reduction on this course’s tiny repo. Your number is yours: it depends on how much of your context was rule text to begin with. The lab below has you measure it rather than quote it.

Demo 4 — the Before/After Measurement

The sample monorepo's init.sh built a branch for exactly this comparison: flat-claude-md squashes the root CLAUDE.md and every services/*/CLAUDE.md into one fat root file — the layout most teams start with. main keeps the nested, scoped layout. Same rules, two shapes.

Measure the flat layout first:

cd ~/labs/refund-monorepo
git checkout flat-claude-md
claude

> /clear
> /context

Record the Memory files category — one entry, the fat root CLAUDE.md, every rule for every service loaded whether this session needs them or not. The captured run (trimmed to the two tables that matter):

That is the measured delta: 2.6k flat vs 817 scoped — the Memory-files category is 68.6% smaller before any work has happened. Then touch one payments file to trigger the lazy load: 

> Read services/payments/README.md and summarize what this service does.
> /context

Here the instrument has a blind spot, and it is worth teaching precisely. On CLI 2.1.218 the lazily loaded services/payments/CLAUDE.md does not appear in /context’s Memory Files table — that table shows the files loaded at session launch. The proof that the lazy load happened is the InstructionsLoaded hook log from Demo 3 (load_reason: "nested_traversal", triggered by the payments README), and /context shows the cost indirectly: the Messages category grew from 8 to 4.2k tokens after the read, because the freshly loaded rules ride there. Gateway and notifications rules stay on disk, unloaded — the hook log stays silent about both.

Two /context readings plus one hook log, one story: the flat branch pays the full rule bill at launch; the scoped branch pays a small baseline — 68.6% less — and then only for the service in play, at the moment it comes into play.

Lab 4 — Your Own Numbers

Easy

Reproduce the Demo 4 comparison on your machine: measure the Memory-files category on flat-claude-md and on main (after /clear, before touching any service), and compute your percentage saving on that category.

Hard

On main, trigger a nested CLAUDE.md load, work until you can run /compact mid-session, and show from the /context output that the nested rule file is no longer loaded. Then recover it with /clear + /catchup and prove from /context that it is back. If no new row appears in /context’s Memory Files table (observed on 2.1.218 for mid-session lazy loads), the InstructionsLoaded log from Demo 3 is the witness.

You succeeded when: you have two Memory-files numbers — flat and scoped — and can explain the delta between them.
